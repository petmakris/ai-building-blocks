Block 09 · Workflows and agent loops

An agent is a loop of model calls. Your code sets its limits and decides when it stops.

A person asks a bills assistant to mark the electricity bill paid and say what is still due. The model, the AI that writes the replies, searches, asks to mark the bill paid, lists what is due, then answers. That takes four paid model calls, in an order no line of code wrote. Each call resends the whole conversation, so each costs more than the last. A confused model would simply keep going.

The whole picture

The idea

An agent is a loop in which the model picks the next tool call, and your code owns its exits, its checks and its saved state.

An agent is like a queue consumer whose commands come from the model. The comparison breaks in three places. No code knows which command comes next, so your code must save where the loop stopped, or a crash loses it. Every command must be checked before it runs. Every command costs money.

Each step in full, with its sources
Step 1

Check the cap, then ask the model

The system prompt is the standing instructions your code writes. The tool list names each of your functions, says what it does and gives a JSON Schema for its arguments. The model cannot run anything. It replies with a tool call: a structured field naming a function and its arguments.

F2.2 · F2.3 · F2.4 · F1.2 · X9 · N6 · C5 · C6 · C9

Step 2

Run the read at once and send everything back

A read-only tool runs straight away. The model remembers nothing between calls. So call 2 resends call 1, its reply and the result. Each call costs more than the one before.

Each tool call carries an id, and Billpod answers every id with a result. The provider, the company that runs the model, rejects a request that leaves an id without one.

F2.5 · F2.6 · F3.5 · C2 · C7 · X8 · E3

Step 3

Check the write against stored data before showing it

Text the model reads can carry instructions it may follow. This is called prompt injection. So a tool call is only a proposal. It must be on the allow-list of tools this loop may run, and match its schema. It must name a bill in this household. It must also carry the bill's version number that the model read, which proves nobody changed the bill meanwhile.

F2.7 · F2.8 · F3.6 · C26 · C27 · C28 · C29 · X14

Step 4

Save the paused loop and end the request

Marking a bill paid changes existing data, so it needs the person's yes. The loop puts the transcript, the results, the call count and the checked arguments into a resume token. That is a string encrypted with AES-256-GCM, which the browser holds but can neither read nor change. The loop shows a card, and the HTTP request ends. Nothing has been written yet.

F2.9 · F3.8 · C30 · C33 · C47 · X16 · N15

Step 5

Resume once and run exactly what was checked

The second request opens the resume token. The token works once, so a second click gets 409. The loop runs the sealed arguments, never new ones from the browser. The count comes from the token, so 2 of the 6 model calls are already used.

F2.10 · F2.11 · F2.12 · F4.3 · F4.4 · F4.6 · C20 · C34 · N7 · N17

Step 6

Stop when a reply has no tool call

Call 3 asks for list_due. Call 4 answers in plain text, and the loop ends. That is 4 of the 6 model calls, across two HTTP requests, and no code wrote "search, then mark paid, then list".

Take away

5 things to remember

1

A workflow keeps the order in code

A workflow is your code calling the model in an order you wrote. Your code owns every exit. Use one whenever you can write the steps down.

C12 · M1
2

An agent stops on a reply with no tool call

That is its only built-in exit. Everything else is yours to add.

C13 · F1.4 · P3
3

Every loop needs caps it reads

A step cap, a timeout per call, and the model tokens used so far, priced into money before each step. Prove them with a fake model that never stops.

C20 · C21 · C24 · E8 · M7
4

Tool calls are proposals

Allow-list them, check them against stored data and version, and have a person confirm each change to existing data.

C26 · C27 · C28 · C30 · M3
5

Save a paused or long run

A restart from step 1 pays every call again and repeats every email or payment.

C33 · C35 · F12 · E12 · M6

The trap

Resetting the step count when the person approves

What people assume

"The approval is a new HTTP request, so the loop starts again with 6 model calls."

Each request gets its own fresh budget, as with a rate limit per request.

What actually happens

A loop that pauses can then make more calls than its budget.

Save the count in the paused state and carry it on. Billpod keeps it in the resume token. Billpod makes one exception to the cap: a resumed request at 6 of 6 gets one extra call, so the model can say what happened. It never gets a fresh 6.

Build it

The smallest agent is a while loop with three exits and one pause

Cap the steps, the cost and the request's time, ask the model, run reads, check writes, pause for a person, and stop on plain text. This Java sketch shows the loop. It is a teaching sketch, not production code.

Instant deadline = Instant.now().plus(REQUEST_TIME);         // 1 this HTTP request only
while (true) {
  if (usage.steps() >= MAX_STEPS) throw new LoopLimitException("steps"); // 1 e.g. 6
  if (usage.cost() >= MAX_COST || Instant.now().isAfter(deadline))
    throw new LoopLimitException("budget");                   // 1 model tokens priced into money
  Reply reply = model.call(SYSTEM_PROMPT, messages, TOOLS, Duration.ofSeconds(60)); // 1 per-call timeout
  usage.add(reply.usage());                                   // 1 one step + priced tokens
  if (reply.toolCalls().isEmpty()) return Result.answer(reply.text()); // 6
  messages.add(Message.assistant(reply.text(), reply.toolCalls()));
  Map<String, Object> results = new LinkedHashMap<>();        // call id → result
  ToolCall pending = null;
  for (ToolCall c : reply.toolCalls()) {
    Tool t = ALLOWED.get(c.name());                           // 3 allow-list
    if (t == null) results.put(c.id(), UNKNOWN_TOOL);         // 3 error result, nothing runs
    else if (t.readOnly()) results.put(c.id(), execute(t, c)); // 2
    else if (pending != null) results.put(c.id(), NOT_RUN);   // 4 a second write in one reply: one card at a time
    else { Object problem = check(t, c);                      // 3 schema, record, version
      if (problem != null) results.put(c.id(), problem); else pending = c; }
  }
  if (pending != null) return Result.card(store.save(messages, results, pending, usage)); // 4
  messages.add(Message.toolResults(results));                 // 2 one result per call id
}

Each [n] marks the code for walkthrough step n. Step [5], the resume, is a second method, not shown. It takes the saved state once and runs the checked call. Then it calls the loop again with a new deadline, carrying over the steps and cost. Unlike Billpod, this sketch gives a resume no extra call at 6 of 6. One gap before production: there is no stored trace of each step, so a bad answer cannot be replayed.
