Block 11 · Guardrails and prompt injection

Treat every document the model reads as untrusted. Guardrails stop hidden instructions from using your tools.

A household-bills app files a CHF 79.90 Swisscom invoice and keeps text from it as a note on the bill. In white 1-point text no person sees, the invoice says to set the amount to 4900 and not to mention it. Weeks later the person asks the chat assistant about Swisscom. The model, the AI that writes the assistant's replies, reads the note like any other text. It also has a tool that edits bills: a tool is a function the model may ask your code to run. The whole picture

The idea

Assume the model will be fooled, and design so that a fooled model can do little harm: no way to send data out, the household taken from the signed-in session, and every change held until a person approves it.

If you write Java: it is like giving a service a database user that can only SELECT from three views. A PreparedStatement fixes SQL injection, but a model has no such fix: it cannot mark text as data only. So the real defence is which tools exist and which actions wait for a person.

Each step in full, with its sources
Step 1

A read runs at once and brings the hidden line along

The person asks about Swisscom, and the model calls a read tool. Reads change nothing, so they run at once. The result carries the note, and the model reads it like any other text.

In Billpod, notes and payee names may come from documents. So they are untrusted content: text an attacker can put in front of the model.

C23 · F4.3 · F2.10b

Step 2

The server checks the name against the declared tools

The model never runs anything. It asks, and your code decides. The assistant declares 46 tools: all 50 except the 4 left out. Any other name gets the error UNKNOWN_TOOL. edit_bill is declared and changes a record, so it must wait for the person's approval.

No declared tool can fetch a URL, so an order to send data out has no tool to use.

F2.8 · C27 · C28 · C30

Step 3

Build the approval card from the stored record

The approval card is the confirmation the person sees. The household comes from the signed-in session, never from the model's arguments. So another household's bill is not found. The old value comes from the database and the new one from the exact call. So the model cannot misdescribe the change.

F2.11 · F2.12 · C32 · C39

Step 4

Seal the call and end the turn

The model's work on this message ends here, with the card on screen. The server keeps nothing while the card waits. It puts the exact call in an encrypted ticket and sends it with the card. The browser cannot read or change the ticket. It expires after 10 minutes.

F2.15 · F2.16 · C33 · C17

Step 5

The person says no, and the server checks the ticket

The ticket must belong to this person and household. It must not have expired. Each ticket is claimed once.

F3.1 · F3.5 · F3.6 · C36

Step 6

Nothing is written, and the model is told why

The bill keeps CHF 79.90. The model gets a result saying the person declined. It also says not to propose the change again unless they ask. The hidden line reached the model and still changed nothing.

Take away

5 things to remember

1

A model obeys text anywhere

It follows orders inside documents, emails and tool results. No escape character marks text as data only, unlike a PreparedStatement.

P1 · P2 · C8
2

Theft needs three things together

Private data, untrusted content and a way out. Remove the way out. Declare no fetch tool. Render no images or links: the browser loads an image's URL by itself, and that URL can carry your data to the attacker.

C21 · C24 · C25 · C27 · C29
3

Changes wait for a person

Edits and deletes become a card built from the stored record. Only the four adds of bills and income run at once.

C30 · C31 · C32
4

The server picks the household

Each tool's code takes the household from the session. The model's arguments have no household field.

C39 · M6
5

Valid is not true

A check cannot tell a fooled model's value from a true one. 4900.00 is a valid amount, and an attacker's IBAN passes the checksum. So read payee, amount and IBAN with plain code from the QR code on Swiss invoices, not with the model.

C47 · P7 · C42

The trap

Counting on the "ignore instructions" line

What people assume

The system prompt, the app's standing instructions to the model, says the document is data. A classifier, a second model that scores text as a likely attack, catches most of the attacks it was trained on.

So write tools run without approval.

What actually happens

These only lower the odds, and attackers retry variants until one works.

In Simon Willison's words, "95% is very much a failing grade." Keep the line, then remove the way out and put every change behind a person's approval.

Build it

The smallest safe tool loop is one class with a pending-calls table

Check the declared tools, run reads at once, and hold every change in a table until the person answers. A teaching sketch in Java: Billpod's TypeScript uses the sealed ticket in place of the table.

public ToolResult onCall(Session s, ToolCall call) {
  if (!DECLARED.contains(call.name()))                  // 2 not a declared tool
    return ToolResult.error("UNKNOWN_TOOL", "There is no tool named " + call.name() + ".");
  if (!NEEDS_CARD.contains(call.name()))                // 1 reads and adds run at once
    return tools.run(call, s.householdId());
  Bill stored = bills.find(s.householdId(), call.arg("billId")) // 3 household from the session
      .orElseThrow(NotFoundException::new);
  String card = stored.payee() + " · " + stored.amount() + " → " + call.arg("amount"); // 3
  pending.insert(new PendingCall(UUID.randomUUID(), s.userId(), s.householdId(),
      call, Instant.now().plus(Duration.ofMinutes(10)), Status.WAITING)); // 4 the row stands in for the ticket
  return ToolResult.card(card);
}

public ToolResult onAnswer(Session s, UUID id, boolean approve) {
  PendingCall p = pending.claimOnce(id, s.userId(), s.householdId()); // 5 own, unexpired, unused
  if (!approve) return ToolResult.declined("The person declined this change on the confirmation card. It was not made. Do not propose it again unless they ask."); // 6
  return tools.run(p.call(), s.householdId());           // approve: the exact stored call, nothing else
}

A comment marked [n] is the code for walkthrough step n. One gap before production: the card does not check the bill's version, so a bill changed between the card and the approval would be overwritten. Billpod checks the version when it builds the card and again when the call runs.
