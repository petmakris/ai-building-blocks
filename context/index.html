Block 04 · Context engineering

Choose what the model sees on every call. More text gives worse answers.

A language model (the AI that writes the replies) remembers nothing between calls. So every request must carry the conversation again. The easy fix is to send all of it. A context window (the most text one call can carry) of a million tokens holds plenty; tokens are the word pieces a model reads and bills by. In a 2025 test, 18 models answered questions about a long chat better when given only the roughly 300 tokens that held the answers than when given all roughly 113,000.

The whole picture

The idea

On every call, build the model's whole view from scratch: choose, order and trim the text so the smallest set that does the job fits a hard token limit.

In backend terms, it is an endpoint that builds one response object from several sources under a hard size limit. The history is a newest-first paged query. Tool calls (the model asking the server to run a function) are lazy loading. The difference is that the model reads the payload as free text. Order and wording change what it does. A correct but irrelevant field makes its answer worse.

Step 1

The browser resends the whole conversation

The browser holds the chat and sends it with every new message, at most the newest 40. The server stores none of it.

Step 2

Trim the history to a budget, newest first

The server walks back from the newest message, adding up characters. Older messages that do not fit are dropped whole. Model APIs expect turns to alternate, starting with the person. So the kept slice must start on a message from the person, never on a model reply. Characters stand in for tokens because counting characters is free.

A common rule of thumb, unverified, is four characters of English per token. By it, 24,000 characters is about 6,000 tokens.

Step 3

Write in the facts the model cannot know

The model has no clock. The system prompt is the developer's instructions, sent in a field of their own. The server writes into it today's date in the household's timezone, plus the currency and language.

C17 · C8 · F7.4 · M2

Step 4

Call the model with prompt, tools, history and message

The request carries the system prompt, 46 tool definitions (functions the model may ask the server to run), the trimmed history and the new message. The history keeps the text of earlier answers but drops their tool results. The bill id was in those results, so the model asks to look the bill up again.

C16 · F1.12 · F1.14 · C28 · X7 · E1 · E2

Step 5

Fetch the bill fresh, because bills change

Billpod drops old tool results on purpose: a bill shown as unpaid earlier may be paid by now. Fetching only the bill it needs gives the model just the relevant part. The server appends the call and its result to the messages and calls the model again.

C28 · M3 · E3 · F1.21b

Step 6

Pause the loop for the person's yes

mark_paid is on a fixed list of writes that need the person's yes on a card; reads and four plain additions run at once. The server seals the tool calls and results made for this message so far, with large results replaced by a short note, plus the exact mark_paid call, into an approval ticket. The ticket is an encrypted blob the browser can neither read nor change. The server sends the card and ticket, ends the HTTP request and keeps nothing.

C23 · C22 · F1.21 · F1.23 · F1.24

Step 7

Resume from the ticket and stop on a reply with no tool calls

The browser sends the same chat again, plus the ticket. The server restores the tool calls from the ticket, runs mark_paid and calls the model a third time. A reply with no tool calls ends the loop. Billpod also caps the loop at 6 model calls per answer, counted across the pause; a resumed turn always gets one more, so 7 at most.

Take away

4 things to remember

1

The browser carries the conversation

Every request must carry it, because the model keeps nothing. Billpod's browser resends it, and the server stores none of it.

C1 · C20
2

A fuller window answers worse

Irrelevant text lowers accuracy long before the window's token limit. Send the smallest context that does the job.

C26 · C5 · M1
3

Trim whole messages, newest first

Keep the newest that fit a budget, start on the person's message, and never cut one in half.

C18 · F4 · M5
4

Fetch data again, never replay it

Old tool results go stale. Keep a one-line outcome note and let the model read again.

C28 · C19 · M3

The trap

Sending everything because it fits

What people assume

"The window holds a million tokens, so send every bill and the whole chat."

Like extra fields in a JSON payload, they cost a little bandwidth and the consumer ignores them.

What actually happens

Extra text makes the model worse, not only slower and dearer.

Context rot (answers getting less reliable as the window fills) starts long before the limit. In a made-up example, last October's electricity bill sits next to this one, and the model could mark the wrong bill paid. Send the smallest set that does the job and fetch the rest with tools.

Build it

The smallest assembler is one method with a loop

Take the browser's chat, trim it, add the facts the model cannot know, and loop over tool calls with a cap. Billpod's real code is TypeScript; this is a Java teaching sketch of the same order of steps, not production code.

public Reply answer(List<Message> fromBrowser, Household h) {    // 1 the browser sends the chat
  List<Message> history = trimNewestFirst(fromBrowser, 24_000);  // 2 whole messages, start on user
  String system = RULES + "Today is " + h.today() + " (" + h.zone() + "). Currency: " + h.currency(); // 3
  List<Message> transcript = new ArrayList<>();
  for (int step = 0; step < 6; step++) {                          // 7 stop after 6 calls
    ModelReply r = gateway.call(system, TOOLS, concat(history, transcript), MAX_OUTPUT_TOKENS); // 4 2048
    if (r.toolCalls().isEmpty()) return Reply.text(r.text());    // 7 no tool calls: done
    transcript.add(Message.assistant(r.toolCalls()));
    List<Result> results = new ArrayList<>(); ToolCall card = null;
    for (ToolCall c : r.toolCalls()) {
      if (card != null && c.isWrite()) results.add(Result.notRun(c)); // 6 one card at a time: later writes are not run
      else if (needsCard(c)) card = c;                           // 6 hold this call for the person's yes
      else results.add(tools.run(c));                            // 5 reads and the 4 additions run now
    }
    if (card != null) return Reply.card(seal(transcript, results, card)); // 6
    transcript.add(Message.tool(results));
  }
  return Reply.text("Stopped after 6 steps.");
}

Each [n] marks the code for walkthrough step n. Resuming from a ticket, the start of step 7, is left out. Like Billpod, the sketch does not log the assembled request. So when an answer is wrong, there is no record of what the model was shown.
