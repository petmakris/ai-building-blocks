Block 12 · Evals

Test AI features with evals. Scored runs over fixed cases show if a change helped or hurt.

A language app asks a model (a hosted service that takes text in and writes text back) whether a learner's French answer is right. The team writes a new grading prompt (the instructions sent to the model) that also underlines the wrong words. The model's reply varies between runs, so a right paraphrase may pass today and fail tomorrow. An answer that drops the "not" may slip through. One assert reply.correct cannot judge this.

The whole picture

The idea

An eval runs an LLM feature (code that sends a prompt to a model and parses the reply) over many real cases and compares its pass rate with a bar written down before the run.

It is a JUnit @ParameterizedTest whose data table is real inputs. It passes on a threshold instead of all green, like a load test's "p95 latency under 300 ms" (a made-up example). One green JUnit run is proof. An eval score is a sample that moves between runs, and its scorer (the code that judges each output) can itself be wrong.

Each step in full, with its sources
Step 1

Load real rows and golden rows

Real rows are learner answers from the staging database. No person has labelled them. Golden rows carry the verdict a person decided is right, plus a note such as "negation lost". Production never sends the model an answer that exactly matches the answer key or an accepted variant. The eval skips those answers too.

Up to 200 real rows and 36 golden rows, 15 of them paraphrases that must be graded right.

Step 2

Run the old and the new prompt on every row

The model picks words with some randomness, so the same row can come back different tomorrow.

Two paid calls per row: up to 236 × 2, about 470 per run.

Step 3

Score real rows against the old verdict

Real rows have no human label, so the old prompt's verdict stands in as the reference. Agreement then measures change only. A disagreement can be a break, or a fix where the old prompt was wrong. A person reads each one.

F1.16 · C17 · C18 · N13

Step 4

Score golden rows against the person's verdict

Correctness comes from here. The golden check needs 95% of golden rows right, and no paraphrase may be graded wrong. Each miss is printed with its note, here "negation lost" and "article error". Neither miss is a paraphrase, so only the 95% bar fails.

F1.17 · F1.18 · F1.19 · C15 · C16 · E2 · N7 · N14 · N15

Step 5

Keep each quality as its own check

Each quality gets its own bar, so a slow right answer never counts as a wrong one. Both checks are plain code. Underlines: when a reply underlines words, at least one must land on a word the learner wrote. A reply with no underlines counts as a pass. The bar is 95% of replies. Speed: 95% of the new prompt's replies must arrive within 2.5 seconds.

F1.20 · F1.21 · C20 · C25 · C39 · C48 · N16 · N19 · Q10 · E13

Step 6

A person reads the misses and fixes the prompt

Each run makes paid model calls, so the eval is a script run by hand. It prints PASS or FAIL per check and exits normally either way. A person reads the result and decides. The golden check failed, so the underlines stay switched off. The bar was set before the run. It is never lowered after a miss.

The underlines sit behind a feature flag, a code switch that is still off today.

Take away

5 things to remember

1

A pass rate replaces one assert

The same code gives different replies, and free text has no single right string. An eval reports a pass rate over many real cases.

C1 · C5 · C6
2

Write the bar before the run

One bar per check, for example 95%. After a miss, fix the prompt, never the bar.

C10 · C25 · M6
3

Real rows measure change only

Agreement with the old prompt says nothing changed. Correctness comes from rows a person labelled.

C17 · Q3
4

Use the cheapest scorer that decides

Exact match, then code assertions. Use an LLM judge, a second model call that grades the output, only after checking it against a person's labels.

C9 · C21 · C23
5

Small gaps are noise

Run both prompts on the same rows and read each row that flipped, instead of trusting the gap.

C30 · C32 · N45

The trap

Treating agreement with the old prompt as correctness

What people assume

"The new prompt agrees with the old one on 95% of real rows, so it is right."

So the team ships as soon as the agreement check passes.

What actually happens

Agreement only means nothing changed.

The old verdict is a stand-in, not the truth. An error both prompts share counts as a pass, and a real fix counts as a failure. Score correctness on rows a person labelled. When the new prompt fixes a real row, add that row to the golden set with a person's verdict.

M7 · Q3 · C17 · C18

Build it

The smallest eval is a CSV file and a loop

Label 30 to 50 real inputs in a CSV, with the expected verdict and a note, and loop them through your real prompt and model. This Java sketch is a teaching sketch, not Lomem code. grader is your existing service that calls the model and parses its reply.

record Case(String answer, String key, boolean expectedRight, String note) {}
List<Case> cases = loadCsv("golden.csv");                  // 1 30-50 labelled real inputs
int right = 0, fast = 0;
Map<String, Integer> failsByNote = new TreeMap<>();
for (Case c : cases) {
    long start = System.currentTimeMillis();
    Verdict v = grader.grade(c.key(), c.answer());         // 2 real prompt, real model
    if (System.currentTimeMillis() - start <= 2500) fast++; // 5 speed is its own check
    if (v.correct() == c.expectedRight()) right++;         // 4 against the person's verdict
    else {
        failsByNote.merge(c.note(), 1, Integer::sum);
        System.out.println("FAIL [" + c.note() + "] " + c.answer()); // 6 read every miss
    }
}
double rightRate = (double) right / cases.size(), fastRate = (double) fast / cases.size();
System.out.printf("verdict %.1f%%, speed %.1f%%, fails %s%n", rightRate * 100, fastRate * 100, failsByNote);
System.out.println((rightRate >= 0.95 ? "PASS" : "FAIL") + " verdict, " // 6 a person decides
    + (fastRate >= 0.95 ? "PASS" : "FAIL") + " speed");     // bars written before the run
System.exit(rightRate >= 0.95 && fastRate >= 0.95 ? 0 : 1);

Each [n] marks the walkthrough step it stands for. The 95% bar and the 2.5-second limit match steps 4 and 5. The sketch runs one prompt and has no old one, so it has no step 3. It also leaves out the underline check. Unlike the Lomem gate, it exits 1 when either rate misses its bar. One gap to fix before production: each case runs once, so a row that flips by chance looks like a real miss. Re-run the misses before trusting them.
