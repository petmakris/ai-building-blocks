Block 03 · Prompts as versioned configuration

Treat prompts as versioned configuration. Keep each one in one place, with a version.

Tunatutor, a language-tutor app in the Lomem repo, sends a block of teaching rules to the model, the AI that writes the replies, on every call. That text is the first block of the prompt; code adds more blocks after it. The rules live in code and also in a database row, so an admin can edit them. A seed script, the SQL that fills a fresh database, had put an old copy in that row. At startup the app preferred the database copy. Builds passed, tests passed and the replies stayed fluent. Only a linguist reviewing replies noticed that two rules never showed up.

The whole picture

The idea

A prompt is configuration that changes what the feature does, so keep one copy, test the exact text the model reads, stamp its version on every result, and be able to roll it back.

A prompt template is like a string in an i18n message file: text with named slots filled per request. The difference is that the model decides what the text means, not your code. So you learn what an edit did only by running many inputs.

Step 1

Register the code copy before reading anything

The app records the prompt's key, its default text in code, and the 8 placeholders ({{name}} slots) that code fills. Engineers review this code copy in git.

Step 2

Load the database row into the cache

Each process keeps the row's text in memory, so building a prompt reads the cache, not the table. Before the fix, startup ended here and the row won. Steps 3 to 5 are the fix.

F1.2 · F1.3 · C44 · F11.2 · N2

Step 3

Compare the cached text with the code copy

If the two are equal there is nothing to heal. Here they differ, so the app must decide which copy wins.

F1.5 · F1.5a · C26

Step 4

Ask whether a person ever edited the row

Every admin save that changes the text first copies the old text into an archive table. Zero archived versions means no person changed it, so the code copy wins. A count above zero keeps the admin's text.

F1.7 · F1.7a · C27 · X14 · E5

Step 5

Reset the row without writing an archive

The heal writes the code copy over the row. It writes no archive row, because an archive row would make the row look admin-edited and stop later heals.

F1.8 · F1.9 · X13 · E6 · M3

Step 6

Fill the slots and send the whole prompt on each turn

A session reads the rules from the cache once, when it is created or reopened. On every turn, code computes the 8 slot values from the learner's level and the practice scene. The filled text goes to the model with every call.

F2.0 · F2.3 · F2.4 · F2.8 · C7 · C6 · N16

Step 7

Stamp the prompt version and model on the result

Tutor replies carry no stamp today. Tunatutor's other prompt, the lesson-note writer, does. It saves its prompt version and the model id (the vendor's exact model name) in two columns on each note. Months later you can see which prompt and which model wrote a bad note.

Take away

4 things to remember

1

A prompt edit changes behaviour

The model reads the text on every call. No compiler or type check sees an edit, and a wrong prompt still gives fluent replies.

C9 · C12 · P1 · P4
2

Keep one copy, decide who wins

Tunatutor's rule: the code copy wins unless an admin edited the row. A startup heal resets unedited stale rows.

C24 · C26 · X17
3

Version the rendered text

Change the version on any change to the text the model reads, including the code that fills a slot. Store the model id in its own field.

C13 · C14 · M4 · M5
4

Golden tests pin text only

A golden test compares the rendered prompt byte for byte with a saved file. To learn whether replies got better, run an eval, a scored run of fixed inputs on old and new versions, or have a domain expert read replies from both.

C17 · C19 · M9

The trap

Trusting golden tests to catch a stale copy

What people assume

"The golden tests pin the prompt, so a wrong prompt fails the build."

So the database copy feels covered by the same tests.

What actually happens

The golden tests feed in the code copy, never the database row.

In July they stayed green while the model read the stale row. The fix deleted the row from the seed SQL. A drift test now reads that SQL file and fails if it inserts the row, and the startup heal resets a stale row that slips through.

M8 · Q1 · E1 · X21 · X22 · X27 · X17

Build it

The fix is three calls at startup and one small heal function

This is tunatutor's real TypeScript from the Lomem repo, trimmed from X18 and X17. The trim drops a one-off check for one legacy row.

registerPromptTemplate(LAYER1_KEY, {                    // 1 code copy + its slots
  defaultContent: DEFAULT_LAYER1_TEMPLATE,
  variables: LAYER1_TEMPLATE_VARIABLES,
});
await loadTemplateCache(LAYER1_KEY);                    // 2 row text into the cache
await healStaleTemplate(LAYER1_KEY);

export async function healStaleTemplate(key: string): Promise<void> {
  const registration = getTemplateRegistration(key);
  if (!registration) return;
  const content = getCachedTemplate(key);                // 3 compare cache with code copy
  if (content === registration.defaultContent) return;
  const versionCount = await countTemplateVersions(key); // 4 admin-edited? keep theirs
  if (versionCount > 0) return;
  await resetPromptTemplate(key, { archive: false });   // 5 code copy over row, no archive
  await loadTemplateCache(key);
}

Markers [1] to [5] mark where steps 1 to 5 start. One gap before production: tutor replies carry no prompt version. Stamp each reply with a hash of the text it used, because a constant like the lesson notes' "v1" does not change when an admin edits the row.
