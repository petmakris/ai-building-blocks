New AI behaviour reaches users in stages, and production failures become new test cases

An LLM feature can pass every test before release and still go wrong on real users, because real inputs are more varied than any test set and a wrong answer looks exactly like a right one. So AI behaviour is released in stages: it first runs on real traffic without being shown (shadow mode), then a switch turns it on once measured numbers clear a threshold fixed in advance, often for a small share of users first (a canary). Afterwards, what users report and what fails in production is written down as new test cases, so the next change is checked against it.

The words this section uses:

  • A large language model (LLM), or model, is a hosted service, rented from a provider such as OpenAI or Anthropic, that takes text in and writes text back. You call it over HTTP by a name such as gpt-4o, and the provider can change what stands behind that name without telling you. Each call costs money.
  • The text you send it, your instructions plus the data, is the prompt. Teams give each prompt a version, such as draft-reply@8, so they can tell which prompt produced which answer. The same prompt can get a different answer on two calls, because the model picks each next word partly at random.
  • In a chat, a turn is one user message plus the reply to it, and a session is one sitting of turns. A trace is the stored record of one model call (prompt version, input, output), and its trace ID is the key you log to find it again.
  • An eval is a script that runs a feature over a fixed list of eval cases (an input plus the expected answer), scores each output and reports pass rates. It plays the role of a test suite, except that it calls the real model and passes on a rate, not on every case.
  • A bar is the threshold a measured rate must clear, such as "at least 95% of cases pass". It is written down before the measurement, so nobody can move it after seeing the numbers. A usual starting point is the current behaviour's own measured rate, so a change may not make things worse.
  • A flag (feature flag, feature toggle) is a switch in code or config that turns a behaviour on or off without a code change elsewhere.

Lomem ran a second-opinion model on every placement chat without showing its answer

Lomem is a language-learning app (the author's own project, used for the real code below). In its placement chat a tutor, itself a model, asks the learner a few questions, each aimed at one level from A1 (beginner) through A2 and B1 to B2 (upper intermediate). After each answer, code extracts facts from it (was the meaning clear, did it use a paragraph, did it speculate) and records whether the learner handled the question. Rules in code turn these facts into a level, which the code calls D, and the learner sees D.

The team wanted a second opinion. A model used to grade or score something is called a judge. This one receives the learner's answered turns plus the extracted facts, but never D, so it cannot copy it. Its prompt requires a JSON reply holding a level and the numbers of the turns it relied on (its cited turns). Nobody knew whether the judge was better than the rules, so it ran in shadow mode: called on every real chat, answer stored, learner still shown D. This is the end of the judge call:

apps/tunatutor/backend/src/use-cases/level-chat/judge.ts:90-104, commit 8fa41788f (shortened)

    const decided = decideLevel(state).level;
    const comparison = acceptJudge(decided, { level: answer.level, citedTurns: answer.citedTurns }, rows, ...);
    const result = { judgeLevel: answer.level, judgeWouldChange: comparison.judgeWouldChange };
    await deps.saveJudge(input.levelChatId, result);
    return result;
  } catch (err: unknown) {
    rethrowIfUndegradable(err);
    logger.warn(..., "level chat: the shadow judge failed — D stands, nothing is stored");

Three details make this safe:

  • It runs off the request path. The chat code starts the judge in the background, once per chat, and returns the tutor's reply without waiting. The learner sees no extra delay.
  • It cannot break the chat. Any failure is caught and logged, and the chat goes on with D (the two errors rethrowIfUndegradable passes on, such as the daily spending cap, are only logged by the background runner too). The judge writes nothing except its own two columns.
  • It stores the comparison, not only the answer. The columns judge_level and judge_would_change record what the judge said and whether it would have replaced D.

"The judge said something different" is not the same as "the judge is right", so a rule in code, acceptJudge, decides whether a difference is credible. Same level: no change. Two or more levels apart: rejected. One level apart: the judge's cited turns must back it with the rules' own facts. These are real test cases from level-chat/__tests__/policy.test.ts:748-791 (commit 8fa41788f), where the rules said B1:

  • Judge says B2, cites turns 5 and 7. Both were B2 questions, and the facts show a paragraph with speculation and consequence, which meets a B2 pass rule. Accepted: judge_would_change = true.
  • Judge says B2, cites only turn 5. Rejected: moving up needs two cited turns that meet a B2 rule.
  • Judge says A2, cites turn 8, a B1 question where the learner's meaning was not clear. Accepted downwards.
  • Judge says A2, cites turn 1, an A1 question the learner handled. Rejected: that turn says nothing against B1.

Made-up readout after a few hundred chats: 412 chats, judge_would_change in 38 (9%). A person reads the 38 chats and notes, chat by chat, whether the judge or the rules placed the learner right. The bar, written before the reading, might be "the judge is right in at least 30 of the 38". If it clears, a flag makes the accepted judge level the one learners see; if not, the judge is dropped.

This judge was removed with its columns in pull request #624 the same day it was added, before any numbers came in; the design plan had named the risk "Judge never leaves shadow mode", with the impact "Judge spend with no benefit". Because it had only ever run in shadow mode, the removal changed nothing any learner saw.

Ordinary monitoring cannot see a wrong answer

In a classic backend, a broken release shows up as exceptions, 500s or failing tests. A model that gives a learner the wrong level returns HTTP 200 with well-formed JSON, in normal time, on inputs no test set anticipated. Only measuring quality on real traffic shows how it performs, and shadow mode does that before anyone depends on the result.

A new check runs in log mode before it is allowed to refuse anything

Lomem has a model write listening exercises: the learner hears a spoken line, then picks its meaning from several choices. Every generated exercise passes through named guards, plain code checks that refuse a bad exercise. A refused exercise is generated again, which is another paid model call. After three tries the best refused one that may still ship is served, and if none may, the request fails with a 503. A guard that refuses too often therefore makes generation slow, expensive or broken. So a new guard starts in log mode: it writes the refusal it would have made to a guard log and lets the exercise through.

apps/tunatutor/backend/src/session-types/overheard/engine/guards.ts:181-204 (shortened)

/**
 * 'enforce' refuses the item. 'log' writes the refusal it WOULD have made and
 * lets the item through, until `scripts/overheard-guard-rates.ts` shows the rate
 * is under about 15 percent. Switching a guard on is one line here.
 ...
 */
export const GUARD_MODES: Record<GuardName, GuardMode> = {
  structure: "enforce",
  ...
  // Measured 0 percent in every language and band (overheard-guard-rates, 2026-10-07).
  "end punctuation": "enforce",
  // Fairness guards: measured first, switched on one by one under about 15 percent.
  cognate: "log",
  ...

"Band" here means level (A1 to B2). "Fairness guards" refuse exercises a learner could answer without understanding the line. A cognate is a word that looks alike in two languages, such as French restaurant and English restaurant. If the line says "Le restaurant ferme à dix heures" and the right choice is "The restaurant closes at ten" while no wrong choice mentions a restaurant, the learner can pick it by matching one word, so the cognate guard refuses it.

The rate is the share of exercises a guard would refuse, per language and level. A large product reads it straight from the guard log of real traffic. Lomem has too few users for that log to give a rate per language and level, so a developer runs the script named in the comment: it generates exercises in bulk with real paid calls and prints each guard's rate. The 15 percent bar is written in the comment and the script, and every fairness guard stays in log mode until it measures under it. At 15 percent, about one exercise in seven needs a second paid call, and three refusals in a row stay rare (0.15³ is about 3 in 1,000). A guard above the bar is not switched on; a person reads a sample of what it refused. If those exercises are fine, the guard is too strict and is loosened or dropped. If they really are bad, the fix belongs in the prompt that writes them.

A flag turns the behaviour on only after an eval clears its bars

Lomem's translation drill grades a learner's translated sentence with a model, called the grader here (its code calls it a judge too). The drill moved to a new grading prompt that returns right or wrong, a focus (which area the mistake is in, such as word order) and a why (one line of explanation). Those went live with the drill. The new prompt can also return marks, the learner's wrong words, to be underlined on the phone. The marks are held back by a flag:

apps/tunatutor/backend/src/session-types/translation-drill/engine/judge-reply.ts:15-20

/**
 * The switch for the judge's marks. While false, a parsed reply keeps `focus`
 * and `why` and returns `marks: null` (unknown, so the phone draws nothing).
 * Only TR4's PR may flip it to true.
 */
export const TD_JUDGE_MARKS = false;

TR4 is the task in the drill's plan that built the eval scripts/translation-judge-gate.ts (the code calls an eval that decides a flag a gate). The script takes real learner answers that the old prompt graded, pulled from the staging database, plus a hand-written list of cases with known right answers. It runs the new prompt on all of them and checks four bars fixed in its header:

  1. the new prompt's right/wrong verdict agrees with the old prompt's on at least 95% of real answers, and with the expected verdict on at least 95% of the hand-written cases;
  2. at least 95% of the marked words are actually found in the learner's text, so the phone can underline them;
  3. at least 90% of the marked words are really wrong;
  4. at least 95% of replies arrive within 2.5 seconds.

The script prints bars 1, 2 and 4 as pass or fail. For bar 3 it prints every marked word, and a person counts the really wrong ones and writes the count into the pull request beside the output. Bar 1 exposes a gap: the new verdicts reached learners before any gate measured them, so this bar checks afterwards that they did not get worse; the hand-written cases cover places where the old prompt was itself wrong.

The flag itself is an ordinary boolean. What is new is the rule that it changes only when the eval's numbers clear bars written before the run. A test asserts that the flag is false, so flipping it by accident fails the build; the PR that flips it on purpose also changes that test. Turning it off again restores the old behaviour, so the code for the old behaviour stays until the new one has passed several later reruns.

A canary shows the behaviour to a small share of users and compares quality signals

Lomem goes from off to on for everyone. Larger products add a step: a canary shows the new behaviour to a small share of users, compares their outcomes with everyone else's, and widens the share only if nothing got worse. The comparison uses quality signals, measures of what users did with the answer, because only those reveal a wrong answer.

Made-up example: a Spring service that drafts replies to customer emails with a model, moving from prompt version 7 to version 8. A support agent reads each draft and sends it, edits it, or throws it away.

boolean useV8 = Math.floorMod(customerId.hashCode(), 100) < rolloutPercent; // 5, then 25, then 100
String promptVersion = useV8 ? "draft-reply@8" : "draft-reply@7";
Draft draft = modelClient.draft(promptVersion, email);
traceLog.record(draft.traceId(), promptVersion, customerId);
// later, when the support agent acts on the draft:
traceLog.outcome(draft.traceId(), sent ? "sent" : "discarded", editDistance(draft.text(), sentText));
// and when the agent clicks the thumbs-down button on a draft:
traceLog.thumbsDown(draft.traceId());

Hashing the customer ID keeps each customer in the same group, so one person does not see the two versions alternate. editDistance counts how many characters the agent changed before sending. Before starting, the team writes the bar: v8 is worse if its discard rate is more than 3 points above v7's (say 20%). With a 20% rate, two groups of 1,500 drafts differ by up to about 3 points from chance alone, so they wait for 1,500 drafts in the v8 group before deciding. If v8 is worse, rolloutPercent goes back to 0 and the bad drafts are read to find out why. Error rates and latency are not the signals, because a bad draft is still a fast 200.

Feedback is useful only when it is stored with the exact turn it is about

Once the behaviour is live, users tell you where it fails. Explicit feedback is what users give when asked: a thumbs-down, a "report a problem" button. Few users ever press it. Implicit feedback is read from what they do (send, edit, discard, retry), as in the canary example, and arrives for almost every response, so it carries far more volume.

Lomem's feedback table holds a rating or a flag with a reason such as wrong_correction. The columns that make a row useful are the ones that tie it to what happened:

  • session_id and turn_index: which session and which turn the complaint is about. Where the session's turns are stored, these two find the exact exchange; a system that does not store turns needs the trace ID here.
  • server_context: a JSON snapshot of the session's state taken by the server at the moment of the click, so the row keeps it after the session moves on. Today only the AI tutor fills it (turn number, the learner's level and languages); other session types leave it empty.
  • status: where the report stands in triage, from open to resolved or won't-fix.

A thumbs-down without these cannot be reproduced and cannot become a test case.

Confirmed production failures are added to the eval as new cases

The loop that closes the system is called the data flywheel: each round of real use produces cases that make the next change safer. A flagged or failed answer is triaged: a person checks whether the model was really wrong, and closes the report as won't-fix if it was not. When two answers could both be right, that person decides which ones the eval accepts, and the case lists all of them. A confirmed failure is written down as a new eval case with its real input and the correct answer, and the next prompt or model change must pass it. In Lomem this is done by hand, and the cases live in a file next to the gate script. One real case:

apps/tunatutor/backend/src/session-types/translation-drill/engine/judge-gate-fixture.ts:28

{ language: "fr", key: "J'ai très faim.", variants: [], answer: "J'ai vraiment faim.",
  expected: "right", markedWords: [], note: "paraphrase: synonym adverb" },

key is the reference translation, variants other accepted translations, answer what the learner typed. Made-up story of how such a row arrives: a learner types "J'ai vraiment faim" for "I am very hungry", the grader marks it wrong, and the learner flags the turn as wrong_correction. The developer opens the feedback row, finds the turn through turn_index, agrees that "vraiment" is a fine synonym for "très", sets the status to resolved, and adds the row above. From then on, every run of the gate checks that the grader accepts this answer.

The loop also has to run when nothing in your code changed. The provider can update the model behind the same name, often without notice, so quality can drift: get worse with no deploy of yours. Only a scheduled rerun catches a silent change. Lomem's gate is run by hand today; the smallest scheduled version is a weekly CI job that runs the eval and alerts the feature's owner when a bar is missed. Its cost is cases times price per call: made-up, 300 cases at $0.002 a call is $0.60 a run. If a rerun misses a bar, the flag goes back off, users get the old behaviour, and the failing cases stay in the eval.

The smallest version fits in one service

Made-up sketch in Java, not Lomem code:

static final boolean NEW_GRADER_ON = false;   // flipped only by the PR that shows the eval results

public Level placement(Chat chat) {
  Level current = rules.level(chat);
  if (NEW_GRADER_ON) return candidateOrCurrent(chat, current);   // after the eval: users see the new result
  shadow.shadowGrade(chat, current);                              // before: fire and forget
  return current;
}

@Async   // a separate thread pool, never the request thread
public void shadowGrade(Chat chat, Level current) {
  try {
    Level candidate = grader.grade(chat);                          // the model call, read-only
    boolean candidateWins = comparisonRule.candidateWins(current, candidate);
    chatRepository.saveShadow(chat.id(), candidate, candidateWins);
  } catch (Exception e) {
    log.warn("shadow grader failed, current level stands", e);
  }
}

Add a thumbs-down endpoint that stores the trace ID (or session and turn) with a snapshot of input and output, an eval file that confirmed failures are appended to by hand, and a scheduled job that reruns the eval. A mature version keeps flags in a flag service (a server such as Unleash that changes flags at runtime, per share of users) and compares canary groups automatically.

The Java analogy: shadow mode is a dark launch, meaning new code deployed to production but not shown to users. GitHub's Scientist library does it by running candidate code next to the current code, returning the current result and logging mismatches. Log-mode guards are a new validation rule deployed in report-only mode. Flags and canaries work as for any service. The flywheel is like a dead-letter queue, where messages that failed processing are parked, if each parked message were turned into a test fixture.

Where it breaks: Scientist counts any mismatch as a bug, but two model answers can both be right, so a mismatch needs a comparison rule such as acceptJudge and a person reading the cases. And quality can drift without any deploy of yours, so the checks never finish.

Common mistakes

  • A shadow call with side effects or on the request path. If it sends an email or writes business data, it is not shadow mode; if the request waits for it, every user pays its delay and its failures.
  • Storing the shadow output but not the comparison. Then nobody can count disagreements later without re-running everything.
  • Deleting the old behaviour when the flag flips. Then a failed rerun leaves nothing to switch back to.
  • Run new AI behaviour in shadow mode first: in the background, without side effects, storing its answer and the comparison while users see the old result.
  • Put new checks in log mode and enforce them only when their measured refusal rate is under a bar set in advance.
  • Flip a flag only when an eval clears bars fixed before the run, and widen it through a canary judged on quality signals (discarded, edited, thumbs-down).
  • Store every piece of feedback with the turn, input and output it refers to, and turn each confirmed failure into an eval case.
  • Rerun the eval on a schedule, and turn the flag off when a bar is missed.
