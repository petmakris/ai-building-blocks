Observability for LLM calls records what the model saw, what it said and what it cost

An LLM call can return a confident wrong answer with HTTP 200, no exception and no log line. Observability for LLM calls keeps one record per call: the exact text sent, the text that came back, the model and prompt version, the token count, the cost and the time taken. On top of those records you sample live traffic, score it, and watch the scores for changes that no deploy of yours explains.

A wrong grade leaves no stack trace

Some terms first. A model (or LLM, large language model) is a service you send text to and get text back from, such as Google's Gemini or Anthropic's Claude. The provider is the company that runs it and sells access through an HTTP API. The prompt is the text you send: fixed instructions written by your team plus the user's data. The fixed part is a prompt template, a text with placeholders that your code fills in; each edit of the template is a new prompt version. Models read and write text in tokens, chunks of roughly three or four characters, and the provider bills you per token, in and out.

The running example comes from Tunatutor, a language-learning app in Lomem, the author's own repository of small apps. In a translation drill, the learner sees an English sentence and types it in Portuguese. Tunatutor sends a model the English sentence, the expected answer and the learner's answer, and the model replies with a score from 0 to 100 and a verdict, correct or not; its instructions give a wrong answer a score of 0 to 50. This section calls that the grading feature.

Made-up incident on that real feature. On a Tuesday afternoon, five learners report the same thing. The drill showed "I am a barista.", the expected answer is Sou barista., and they wrote Eu sou um barista., which adds the pronoun "eu" (I) and the article "um" (a) and is still correct Portuguese. The grading feature marked it wrong. Nothing has been deployed for a week. The application logs show the call took 1.4 seconds and returned 200. The error tracker is empty. To find the cause you need four things the logs do not have: the exact prompt the model received, the exact reply, which model version answered, and whether the mistake happens on other answers too.

In a classic backend a wrong result comes from your code or your data, and a stack trace or a database row points at it. Here the "logic" is the prompt text plus a model you do not run. The evidence is the text that went in and came out, and you only have it if you stored it.

LLM calls create five problems that REST calls do not have

  • The bug is in the text. A wrong answer is usually explained by what the prompt contained: a missing rule, a truncated document, the wrong user's data. You debug by reading the prompt and the reply.
  • Every call has a variable price. Cost depends on how many tokens each call used, so one feature with a long prompt can double the monthly bill with no change in traffic.
  • The prompt changes outside a code deploy. Many teams, Lomem included, store prompt templates in a database so they can edit them without a release. A record that does not say which version ran cannot tell you whether an edit caused a regression.
  • Quality can change when nobody on your team deployed anything. This is called drift. The provider may update the model behind the same name, a provider bug may degrade answers, or your users may start sending a kind of input you never tested. In a 2023 study, GPT-4 (an OpenAI model) identified prime numbers with 84% accuracy in its March version and 51% in its June version, under the same API name.
  • Stored prompts contain your users' words. A prompt holds whatever the user typed, including names, emails and account numbers, so the store of prompts is a store of personal data.

Classic analogy: this is distributed tracing plus APM (application performance monitoring, such as Datadog or New Relic) plus a billing meter. The model call is one more timed downstream call in the request's trace, like a call to a payment provider, with tokens and cost as extra attributes.

Where it breaks: for a payment call, the status code tells you whether it worked. For a model call, success is a judgement about the text, so you need the payload and a score, which APM never stored. A payment API also behaves the same until it announces a new version; a model behind the same name can answer differently next week. And APM payloads are rarely personal data, while prompts usually are.

One record per call answers what happened, which version ran, how much and how slow

Every model call goes through one wrapper in your code, and the wrapper writes one record per call, failed calls included. The record carries the trace ID: the ID your tracing library (Micrometer Tracing, which Spring Boot uses, or OpenTelemetry) gives each incoming request and passes to every downstream call. Inside a trace, each timed operation, such as one outgoing HTTP call, is a span. A background job starts a new trace when it starts. The wrapper does this:

  1. Before the call, note the start time and the current trace ID.
  2. Record the request: provider, requested model name, prompt template name and version, the feature that made the call, and the user or customer account it is billed to.
  3. Make the call and parse the reply into your own result type, here the score and verdict, so you can query quality without re-reading text.
  4. Read from the reply the model version the provider says answered (Gemini's modelVersion field; model for OpenAI and Anthropic), the token counts and the finish reason, which says why the model stopped: it finished (Gemini says STOP), it hit the length limit (MAX_TOKENS), or the provider's content filter cut it off (SAFETY).
  5. Compute the cost from the token counts and a price table: a model_prices table with the model name, the date from which a price holds, and three prices per million tokens. Someone adds a row when the provider changes its prices. If the responding model has no row, write no cost and count the miss, so a new model name shows up as a gap rather than as a free call.
  6. Write the record to the log. Redact the prompt and reply text (see below) and save it to a separate table keyed by trace ID.

Token counts come in three kinds. Input tokens are the whole prompt. Cached input tokens are the part of the input that matches the start of a prompt the provider received in the last few minutes; it reuses its earlier work on them and bills them at a lower price. Putting the fixed instructions first and the user's data last makes that shared start longer. In Gemini's and OpenAI's counts, and in the OpenTelemetry names below, cached tokens are a subset of the input tokens, not an addition; Anthropic's API reports them in a separate field. Output tokens are the reply.

Made-up example of one record from that Tuesday. The request asks for gemini-flash-latest, an alias (a moving name) that Google points at its newest Flash model; Flash is Google's name for its cheaper, faster Gemini models. The reply names the version that actually answered.

{
  "trace_id": "4f2a9c1e7b0d4c55",
  "feature": "translation_grading", "user_id": 8812,
  "prompt_template": "translation_grade", "prompt_version": 14,
  "provider": "gcp.gemini", "request_model": "gemini-flash-latest",
  "response_model": "gemini-2.5-flash-preview-09-2025",
  "input_tokens": 912, "cached_input_tokens": 640, "output_tokens": 38,
  "finish_reason": "STOP", "latency_ms": 1412, "cost_usd": 0.000196,
  "score": 41, "verdict": "wrong"
}

The cost, with made-up prices in dollars per million tokens (input 0.30, cached input 0.03, output 2.50): 912 − 640 = 272 uncached input tokens × 0.30 + 640 cached × 0.03 + 38 output × 2.50, divided by a million, is 0.000196 dollars.

The provider does not always report a more specific version than the one you asked for. When response_model equals request_model, only the quality scores described further down reveal a silent model change.

The smallest useful version is one structured log line per call

Spring AI, Spring's library for calling models, already emits a Micrometer observation named gen_ai.client.operation for every chat call. A Micrometer observation is one instrumented operation that Micrometer turns into a timer metric and, when tracing is on, into a span. It carries model names, token counts and finish reasons. Prompt and reply text are off by default (spring.ai.chat.observations.log-prompt and log-completion switch them on). You still add the feature, prompt version, cost and parsed result yourself. Without Spring AI, a wrapper is enough:

Made-up example: a minimal wrapper in Java

public GradeResult grade(GradeRequest req, long userId) {
    Prompt prompt = prompts.get("translation_grade"); // name, version, text from the DB
    String text = prompt.render(req);
    String traceId = tracer.currentSpan().context().traceId();
    long start = System.nanoTime();
    ModelReply reply = null;
    GradeResult result = null;
    String error = null;
    try {
        reply = client.call(MODEL, text);
        result = parse(reply.text());
        return result;
    } catch (RuntimeException e) {
        error = e.getClass().getSimpleName();
        throw e;
    } finally {
        try {
            long latencyMs = (System.nanoTime() - start) / 1_000_000;
            // of(...) reads modelVersion, token counts and finishReason from reply, if any
            CallRecord rec = CallRecord.of(traceId, "translation_grading", userId,
                    prompt, MODEL, reply, result, error, latencyMs);
            callLog.write(rec.withCost(prices.cost(rec))); // cost null if model unknown
            callText.save(traceId, redactor.scrub(text),
                    reply == null ? null : redactor.scrub(reply.text()));
            if (error == null && "STOP".equals(rec.finishReason())
                    && Math.floorMod(traceId.hashCode(), 100) < 2) {
                evalQueue.send(traceId); // 2% sample for the online eval, below
            }
        } catch (RuntimeException recordFailure) {
            log.warn("llm_call record failed", recordFailure); // keep the call's own outcome
        }
    }
}

callLog.write logs one line, log.info("llm_call", kv("feature", ...), kv("prompt_version", ...), ...), with one pair per field of the record and null where a failed call has no value. kv comes from logstash-logback-encoder, a Logback encoder that writes each log line as JSON and each kv pair as a field. The inner try makes sure a failure while recording never replaces the model call's own result or exception.

callText.save writes to an llm_call_text table with four columns: trace_id, created_at, the redacted prompt and the redacted reply. A nightly job deletes rows older than 14 days, and only the engineers on call can read it. That window is what lets you read the five barista prompts when the reports arrive. The metadata goes to your log pipeline and is kept as long as your logs.

OpenTelemetry's GenAI conventions give these fields standard names

OpenTelemetry is the open tracing standard most monitoring tools read. It publishes semantic conventions for GenAI: agreed attribute names, so any tracing backend understands your spans. A model call is a client span (a span for a call your service makes) with attributes such as gen_ai.provider.name, gen_ai.request.model, gen_ai.response.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens and gen_ai.response.finish_reasons. Prompt and reply go in gen_ai.input.messages and gen_ai.output.messages, which are opt-in because, in the spec's words, the input "is likely to contain sensitive information including user/PII data" (PII: personally identifiable information). The conventions are marked "Development", so names can change between releases. Prompt template and version have their own attributes, gen_ai.prompt.name and gen_ai.prompt.version, and cached input tokens go in gen_ai.usage.cache_read.input_tokens. Use these names for your log fields too, and the record moves into spans later without renaming. If it does, keep the text in the restricted table unless your tracing backend has the same short retention and narrow access.

Drift is detected by scoring a sample of live traffic every day

Latency and error alerts do not fire on drift, because a drifted answer is fast and returns 200. You need a quality number per day, computed on real traffic. An eval is a check that scores a model's answers; an online eval runs on live production calls rather than a fixed test set:

  1. Sample. The wrapper's last lines send the trace ID to a queue when the trace ID's hash modulo 100 is below 2. Trace IDs are random, so this is a random 2%, and every instance makes the same choice for the same ID. Calls that failed, or stopped at MAX_TOKENS or SAFETY, are not scored; you chart their rate straight from the log records.
  2. Score, off the request path. A queue consumer reads the call's text from llm_call_text within minutes. It scores it with a deterministic check where one exists: plain code with a fixed answer, such as "is the score between 0 and 100". Otherwise it asks a second model, the checker model, to judge the answer against a rubric, a written list of what counts as correct. Use a strong model pinned to a fixed version name, so the checker does not change along with the model it checks, and send its calls through the same wrapper under their own feature name so their cost is logged too. A person can also score.
  3. Store. The consumer writes an llm_eval row: trace_id, eval_score, the checker and rubric version, and the time. You join it to the log records by trace ID. Scores hold no user text, so you keep them for months.
  4. Chart and alert. Chart the daily average per prompt version and per response model. Alert when a day falls below its usual band, for example three standard deviations (a measure of how far the daily figure usually moves) below the mean of the last 30 days. A rise is worth a look but needs no alert.

The sample must be big enough. A daily rate p measured on n scored calls moves by about √(p(1−p)/n) by chance. With p = 0.95 and n = 200 that is √(0.95 × 0.05 / 200) ≈ 0.015, or 1.5 percentage points. Set the sample rate per feature to reach about 200 scored calls a day: 2% of 10,000 calls, or 20% of 1,000. A feature with fewer calls is scored in full or charted per week.

Made-up example. The checker model gets the English sentence, the expected answer, the learner's answer and the grading feature's verdict, plus a rubric: "A word the expected answer leaves out that keeps the meaning, such as the pronoun 'Eu' or the article 'um', a one-letter typo in a long word, or formal versus informal 'you' does not make a translation wrong. Reply AGREE if the verdict is correct under these rules, otherwise DISAGREE." Nobody has to write the correct verdict for each sampled call in advance. The consumer stores AGREE as 1 and DISAGREE as 0, and rejects any other reply as a failed check. The daily average is the agreement rate. For the last 30 days it sat between 0.94 and 0.97, and the band puts the alert at 0.92.

Made-up end of the incident. On Monday morning Google moves the alias gemini-flash-latest to gemini-2.5-flash-preview-09-2025, a pre-release version. At 06:00 on Tuesday the nightly chart job computes Monday's agreement rate, 0.81, and alerts the feature's owner, hours before the learners write in. The owner groups the "wrong" rate in the log records by day, prompt_version and response_model. Up to Sunday every call has response_model gemini-2.5-flash and a "wrong" rate of 4%. From Monday it is the preview model and 19%. prompt_version is 14 throughout, so the prompt did not change; the model behind the name did. The team sets request_model to the fixed name gemini-2.5-flash. A model can give a different reply to the same prompt on each run, so they send each of the five stored prompts ten times; all fifty runs pass. The barista case goes into their test set.

When the provider reports no specific version, keep a fixed set of a few dozen old prompts with known-good answers and replay them each day. If the old prompts start failing too, the model changed. If they still pass while live scores fall, your users' inputs changed.

A random sample gives the rate you chart. A targeted sample of uncertain answers finds problems with fewer human reviews; use it in addition. Lomem has a hand-made one: in a Tunatutor checkpoint (a level test), every answer scored between 50 and 85 is logged for a person to review, because just above the "wrong" line is where the grading is least sure (apps/tunatutor/backend/src/session-types/translation-drill/engine/checkpoint-rules.ts:63-76). It logs the learner's own answer into the normal production log, which is the next problem.

Prompts and replies must be redacted by content before they are stored

Classic log redaction removes fields by name: password, token, authorization. That cannot help with model text, because a prompt is one long prose field. Scrub the text itself, inside the wrapper before the write. Pattern matching catches emails, phone numbers and IBANs (international bank account numbers). A detector library such as Microsoft Presidio also finds names. Made-up example: my name is Ana Silva, write to ana@example.com becomes my name is <PERSON>, write to <EMAIL>. The checker model reads only this redacted text. Keep prompt text in its own store with short retention and restricted access. Keep the metadata (tokens, cost, versions, scores) longer, since it holds no user text. Whether the unredacted prompt may be sent to the provider at all is a contract question with that provider.

A mature setup adds nested spans, dashboards, feedback and replay

  • One span per model call when a request makes several, all under one trace.
  • Dashboards of cost, latency, finish reasons and eval scores per feature, prompt version and model.
  • User feedback (thumbs up or down, a support ticket) attached to the trace it is about.
  • Alerts on eval scores and on spend per feature per day.
  • Replay of stored, redacted prompts against a new model or prompt version, compared before switching.

Tools such as Langfuse and Arize Phoenix store traces, scores and prompts for you, with a UI to read and score them.

Common mistakes

  • Logging token counts but not the prompt version, so a quality drop cannot be tied to the edit that caused it.
  • Recording the requested model name only. The reply often names a more specific version, and that is the one that changed.
  • Requesting a moving alias such as gemini-flash-latest in production instead of a fixed version name.
  • Storing full prompts in the normal application log, where retention is long and access is wide.
  • Alerting only on errors and latency, which never fire on drift.
  • Running the online eval inside the user's request, which adds a second model call to every response.
  • Write one record per model call, failed calls included, with trace ID, feature, user, prompt version, requested and responding model, input, cached and output tokens, finish reason, latency, cost and the parsed result.
  • Store prompt and reply text separately, keyed by trace ID, redacted by content, with short retention and restricted access.
  • Detect drift by scoring a random sample of live calls off the request path, storing the score by trace ID, and charting it per day, prompt version and model with an alert band.
  • Use the OpenTelemetry GenAI attribute names, including gen_ai.prompt.version for the prompt version.
