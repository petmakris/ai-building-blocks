Context engineering decides what the model sees on every call

A language model answers only from the text sent to it in one request, and that text has a hard size limit. Context engineering is the server code that chooses, orders and trims that text for every call. It exists because the model keeps no state between calls, and because a request that is too full gives worse answers as well as costing more.

The model remembers nothing between two calls

Start with a real feature. Ask Billpod is a chat panel in Billpod, a household-bills app in Lomem, a private codebase of small apps that this guide quotes. A person types two messages, one after the other:

  1. "Did we pay the electricity bill this month?"
  2. "Mark it paid, by e-banking."

Billpod answers each message by calling a large language model (LLM): a remote service that takes text in and returns text out, over an HTTP API like any other. Billpod uses Google's Gemini Flash. The text sent in one request is the prompt. The model has no session and no database. When the second request arrives, the model cannot know what "it" means unless the second request also contains the first question and its answer. Each call is a pure function of its request body.

So the browser keeps the conversation and sends all of it with every new message, and Billpod's server rebuilds the whole model request each time from what arrives. The server stores no conversation:

packages/billpod-shared/src/ai/assistant.ts:6-7

// The conversation lives in the client, not the database: every request
// carries the visible turns (capped below), ...

A turn here is one message, from the person or from the model.

Tokens measure the request, and the window caps it

A token is the unit a model reads and bills by: a word or part of a word, roughly four characters of English on average (fewer characters per token in most other languages). The context window is the most tokens one request can hold, counting the input you send and the answer the model writes. Current models allow 200,000 to about 1,000,000 tokens; Gemini Flash models accept about one million. The limit is enforced: Anthropic's API, for example, rejects an input over it with HTTP 400 "prompt is too long", and other providers return a similar error. Everything in the request counts: instructions, past messages, tool descriptions and data. Because the answer counts too, each request also sets maxTokens, the most tokens the model may write in reply; Billpod sets 2,048. A model that reaches that cap stops mid-sentence, and the response says it stopped for that reason. Every response also reports how many tokens the request used, but only after the call; Billpod adds these up for billing.

Context engineering is the code that decides what goes into that window on each call.

Each request is assembled from five layers

A model API request carries three fields of content, plus settings such as maxTokens. The system prompt is a separate field of instructions that apply to the whole conversation, written by the developer and never shown to the person. The messages are a list, each with a role: user for the person, assistant for the model's replies, and tool for data the server sends back. The tool definitions describe functions the model may ask the server to run: a name, a description in plain words, and a JSON Schema for the arguments (the same JSON Schema standard Java validators use; the model usually follows it, but the server must still validate the arguments). A tool call is the model's way of asking: instead of only text, its reply carries a structured list of calls such as {"name": "find_bills", "args": {"text": "electricity"}}. The server runs that function and sends the result back in the next request. The model never touches the database itself.

Ask Billpod fills five layers, fresh for every message. The first two are the system prompt and tools fields; the last three all go into the messages list, in this order:

One answer can take several model calls. Made-up values in Billpod's real request shape. Billpod builds this provider-neutral JSON; one class in Lomem's shared LLM code (GeminiProvider) translates it into Gemini's HTTP format, which has the same parts. The person sends "Mark it paid, by e-banking." The server's first request:

{
  "systemPrompt": "You are Ask Billpod ... Today is Tuesday, 2026-10-13, in the household's
                   timezone (Europe/Zurich). The household currency is CHF. ...",
  "tools": [ { "name": "find_bills", "description": "Search the household's bills ...",
               "parameters": { ...JSON Schema... } },
             { "name": "mark_paid", ... }, ... ],
  "messages": [
    { "role": "user",      "content": "Did we pay the electricity bill this month?" },
    { "role": "assistant", "content": "Not yet. The electricity bill, 84.20 CHF, is due on 20 October." },
    { "role": "user",      "content": "Mark it paid, by e-banking." }
  ],
  "maxTokens": 2048
}

The model's response has the same shape every time: some text, a list of tool calls (possibly empty), a reason it stopped, and the tokens used:

{ "text": "", "toolCalls": [ { "id": "c1", "name": "find_bills", "args": { "text": "electricity" } } ],
  "stopReason": "tool_use", "usage": { "inputTokens": 9120, "outputTokens": 18 } }
  1. Call 1. The answer to the earlier question had looked the bill up, but the history keeps only that answer's text, so the bill's id is gone. The model therefore asks for find_bills again, as above. Any text that comes with tool calls is shown to the person as it arrives.
  2. Call 2. The server runs the calls in order and sends the same request with two messages appended. The result names the id of the call it answers: 
        { "role": "assistant", "toolCalls": [ { "id": "c1", "name": "find_bills",
                                            "args": { "text": "electricity" } } ] },
    { "role": "tool", "toolResults": [ { "callId": "c1", "name": "find_bills",
        "response": { "result": [ { "id": "b_19", "version": 3, "amount": "84.20", ... } ] } } ] }
    version is the bill's optimistic-locking version: a write that names an old one is refused. If the model names a tool that does not exist, or a tool fails, the error goes back as that call's result, and the model can try again. This time the model replies with mark_paid {"billId": "b_19", "version": 3, "paidVia": "e-banking"}.
  3. A pause for the person. A fixed list in Billpod's code names the writes that need the person's yes: mark_paid, deletes, every edit of an existing record, and every write to the household's people, categories, members and paperwork. Reads and four plain additions (add_bill, add_recurring, add_income, add_recurring_income) run at once. So the server does not run mark_paid. It shows a confirmation card and sends the browser an approval ticket: an encrypted and authenticated blob (AES-256-GCM, valid for 10 minutes) the browser can neither read nor change, holding the messages of Calls 1 and 2 (large tool results replaced by a short note) and the exact mark_paid call, then ends the HTTP request, keeping nothing.
  4. Approve and Call 3. The browser sends the same conversation again, plus the ticket. The server runs the sealed call and makes Call 3 from the history, the new message, the messages from the ticket and the mark_paid result. Calls 1 and 2 are not repeated. The model replies "Done: the electricity bill is marked paid" with an empty list of tool calls, which ends the loop.

The rule: call the model, run whatever tools it asks for, append the calls and results, call it again, and stop when the reply has no tool calls. Billpod caps this at 6 model calls per answer, counting the calls before a pause; past the cap the person sees "Stopped after 6 steps."

The history is cut to a budget, newest message first

A long chat would eventually overflow the window, and long before that it would cost more on every message. Billpod caps the history at 24,000 characters, roughly 6,000 tokens. The system prompt and the tool definitions come on top and are not counted in it:

packages/billpod-shared/src/ai/assistant.ts:20-21

  /** Total characters of history sent to the model; older turns are dropped first. */
  maxHistoryChars: 24_000,

The browser sends back only what the person saw: the text of each message and, for each model answer, the writes it made. Each write is a one-line summary the server sent at the time, plus an outcome such as done or declined. The server turns each message into one {role, content} text message (the code calls this list rendered), appending a line such as [What happened to your changes in this turn: mark_paid (electricity): done] to an answer. Tool calls and results of earlier answers are left out. The browser could alter these notes, but they only steer the model; the facts are read again through tools. Then the trimming walks backwards from the newest message, with budget set to 24,000 (x! tells the TypeScript compiler that x is not null):

apps/billpod/backend/src/ai/assistant/history.ts:36-45

  let used = 0;
  let from = rendered.length;
  for (let i = rendered.length - 1; i >= 0; i--) {
    const cost = rendered[i]!.content.length;
    // The newest message (the person's question) is always kept.
    if (i < rendered.length - 1 && used + cost > budget) break;
    used += cost;
    from = i;
  }
  while (from < rendered.length - 1 && rendered[from]!.role !== "user") from++;

Made-up example. Seven messages, oldest first: user 2,000 characters, assistant 6,000, user 2,000, assistant 6,000, user 2,000, assistant 6,000, and the new user message of 40. Walking back, the running total is 40, 6,040, 8,040, 14,040, 16,040, then 22,040 with the oldest assistant message. Adding the oldest user message would make 24,040, over 24,000, so the walk stops there. The kept slice would then start on an assistant message, so the last line moves it forward one step. Five messages, 16,040 characters, go to the model.

Three rules follow. The newest message always survives; Billpod's own request validation also rejects a typed message over 2,000 characters and a stored answer over 6,000, so one message can never exceed the budget alone. Older messages are dropped whole, never cut in the middle. The kept slice starts on a user message, because model APIs expect the roles to alternate, starting with the person. For the same reason, when an empty answer is dropped and two messages of one role end up side by side, Billpod joins them into one.

Characters are used instead of tokens because counting them is free and needs no call to the provider. The estimate is rough, and non-English text costs more tokens per character, but 24,000 characters is far below a one-million-token window, so the margin absorbs the error and keeps Billpod far from the "prompt is too long" error. The budget is set by cost and answer quality, not by the window: roughly 6,000 tokens of history per call is cheap, and it holds several full exchanges.

A fuller window gives less reliable answers

A classic backend gets no worse at its job when the payload grows. A model does. Made-up example: if Billpod sent all 300 of a household's bills with every question, the window would hold last October's electricity bill next to this one, and the model could mark the wrong one paid. Measured evidence: in a 2025 study by Chroma, a company that makes a search database, 18 models answered the same questions about a long chat twice: once given the full history of about 113,000 tokens, once given only the relevant part, about 300 tokens. Every model answered more questions correctly from the short version. In a separate test of the same study, passages that looked relevant but were not, called distractors, lowered accuracy further: even one distractor hurt. This effect is called context rot: as the window fills, the model finds and uses the right facts less reliably. So the budget limits quality as well as size and cost, and the aim is the smallest set of tokens that lets the model do the job.

Load data when a question needs it

Billpod sends none of the household's bills up front. The system prompt tells the model to fetch facts through tools:

apps/billpod/backend/src/ai/assistant/prompt.ts:37

    "- Use the tools for every fact. Never guess an amount, a date, or whether something is paid.",

The data enters the window only when a question needs it, and old tool results are not carried forward:

apps/billpod/backend/src/ai/assistant/history.ts:4-5

// assistant made or proposed. Earlier turns' tool results are not replayed:
// household data changes, so the model reads it again when it needs it.

This saves tokens and keeps stale data out: a bill listed as unpaid ten minutes ago may be paid now. That is why the model called find_bills again in Call 1. Anthropic calls this just-in-time loading: keep small references (an id, a file path, a query) in the window and fetch the content with a tool when needed.

Long-running agents compact, clear and delegate

Billpod's chats are short, so a 24,000-character cut is enough. An agent is a model that calls tools in a loop for many steps, for example a coding assistant reading a whole repository. Its window fills much faster, mostly with tool results. Lomem uses none of the following; they come from Anthropic's write-up on context engineering:

  • Compaction. When the token count reported by the last response shows the window is nearly full, ask the model to summarise the conversation so far, keeping decisions and open problems. Every later request then sends that summary in place of the full history.
  • Clearing old tool results. Replace the raw output of a tool called many steps ago with a short placeholder.
  • Notes outside the window. The agent writes progress to a file or table and reads it back later, so facts survive a compaction.
  • Sub-agents. A sub-agent is a separate model conversation, with its own empty window, that the main agent hands a search to. It may read tens of thousands of tokens but returns only a summary, "often 1,000-2,000 tokens", and only that summary enters the main window.

The smallest version fits in one class

The minimum is what Billpod does: one assembler that builds the system prompt with the facts the model cannot know (date, timezone, currency, language), and adds the tool definitions. It adds the newest history that fits a budget, starting on a user message, with a one-line note of each earlier write's outcome, then the new message. It runs the tool loop with a step cap. Billpod logs only failures, not the assembled request. A mature version adds:

  • a log of every assembled request, so a wrong answer can be traced to what the model saw;
  • real token counts from the provider instead of a character estimate, and a log line with each layer's size on every call;
  • a separate budget for each layer, with a rule for which layer is cut first when the total is still too big;
  • stable layers first and changing layers last, because of the prompt cache: when a request begins with exactly the same text as a recent one, the provider reuses its earlier work on that part and charges less for it. Gemini does this automatically; Anthropic's API needs a marker in the request. Billpod's order fits this: its system prompt and tools stay identical for a whole day.

Classic backend analogy. Context assembly is a response assembler: the service method that builds one DTO from several repositories under a hard payload limit. The system prompt is the static part, the history is a paged query sorted newest first, and tool calls are lazy loading: fetch the association only when it is accessed.

Where it breaks. A DTO has a schema, and its consumer reads every field the same way regardless of size. A model reads free text: the order and wording of the layers change its behaviour, and adding a correct but irrelevant field makes its answer worse. There is also no error when something important was trimmed. The model answers anyway, from what is left.

Common mistakes come from treating the window like a payload

  • Sending everything because it fits. Context rot and cost start long before the window is full.
  • Forgetting facts the model cannot know, such as today's date, timezone, currency and language.
  • Replaying old tool results, which waste tokens and can contradict current data.
  • Not logging the assembled request. When an answer is wrong, the first question is what the model was shown.
  • The model is stateless: every call must carry everything it needs, history included, and one answer may take several calls through the tool loop.
  • The context window is a hard token limit for input plus output, and answer quality drops well before it is reached.
  • Build each request in one assembler from layers: system prompt, tool definitions, trimmed history, the new message, and this answer's tool calls and results.
  • Fetch data with tools when a question needs it, and do not replay old tool results.
  • Long agent runs also need compaction, cleared tool results, notes outside the window and sub-agents.
