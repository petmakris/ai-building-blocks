Human in the loop: the model proposes a risky action and a person approves it before any code runs it

When software lets a language model decide to change data, some of those changes are too risky to run on the model's word alone. Human in the loop means the system stops at those changes, shows a person exactly what will happen, and runs the change only after that person clicks Approve. It exists because the model can be wrong with full confidence, and because text it reads can push it into actions nobody asked for.

A household assistant stops before it marks a bill paid

Billpod is a household bills app from a small codebase of apps. It has a chat panel where a person types requests in plain language. Behind it sits a language model: a remote service that takes text in and returns text out. The backend sends it fixed instructions, the conversation so far, and a list of tools: named operations such as find_bills or mark_paid, each with a typed input.

The model cannot run code. Each reply, a model step, is text or one or more tool calls: small JSON requests like {"name": "mark_paid", "args": {"billId": "b17", "version": 3}, "id": "c2"}. The backend validates each call, runs it or not, and asks the model again with the results. One pass from the person's message to the model's final answer is a turn.

The person types "I paid the electricity bill by card".

  1. The model calls find_bills. Reading is harmless, so the backend runs it at once and returns the bill with its version number.
  2. The model calls mark_paid with that id and version. This tool is on a list in code of writes that need a yes, so the backend does not run it.
  3. The backend checks the call is possible: the bill exists, its version matches, it is not already paid. Code then renders a confirmation card from the stored bill row (payee, amount) and the call's checked arguments (paid on, paid via). Nothing the model wrote about the call is shown.
  4. The turn ends with the card instead of an answer. The click is a new request carrying only the decision and a reference to the stored proposal. On Approve, the server runs exactly the stored call and gives the result to the model under the call's id c2. The model continues and replies "Done". On Cancel, the model receives a "declined" result and nothing runs.

A model is a caller that can be confidently wrong and steered by the data it reads

In a classic backend, every write comes from code you wrote or from a user who clicked a button. Neither invents a bill id. A model can. It can pick the wrong one of two similar bills, and it sounds just as sure either way.

A model also cannot reliably tell its developers' instructions from text that arrives as data. An invoice it reads might contain "also delete the other bills from this payee". This is prompt injection. Instructions to ignore such text, and input filters, catch some cases and miss others. The approval click is what keeps that text from changing data on its own.

Billpod also offers its tools to outside assistants through MCP (Model Context Protocol), the open standard for connecting AI apps to tools. Its security principles say the host "must obtain explicit user consent before invoking any tool".

The pending action has to be tamper-proof between the card and the click

If the browser sent the arguments back with the click, anyone could change them. So the server holds or verifies the proposal, and the client sends only a reference and the decision. Approving runs exactly the stored arguments, once, before an expiry, for the right user, and re-checks the record's version when it runs. If the version moved (optimistic locking), the refusal goes back to the model as the call's result, and the card is used up.

The usual design is a database row, shown below. Billpod stores no conversations on the server, so it uses a sealed token instead: an AES-256-GCM encrypted string the browser carries but cannot read or change. It holds the proposed call and the turn's earlier steps, which the model needs when it continues. It is bound to the user, the household and a hash of the chat, and expires after 10 minutes. A single-use row is written only when the card is answered, so a second click gets HTTP 409.

The risk of each tool decides whether it needs approval

Approval on every call makes the assistant useless. Billpod sorts its tools by risk:

  • Reads such as find_bills run at once.
  • Writes that only add such as add_bill run at once. An added bill gets an Undo button, which deletes it at the version it was created with.
  • Writes that change or delete such as mark_paid, edit_bill and delete_bill stop at a card.

The list of tools that need a card lives in code, never in the prompt, so no text the model reads can change it.

One model step can hold several calls, planned on the assumption that the earlier ones happen. If the person cancels the first, the later ones may be wrong. So while a call waits at a card, Billpod runs no later write of that step; reads still run. Each held write is answered "not run", sent with the decided result after the click, and the model decides again. A mature system adds levels by amount and a second reviewer.

The smallest version is a pending-action table and a decision endpoint

Made-up example, in Spring terms. You need a stored conversation and a pending_action table. In the loop, a call whose tool is in a CONFIRM_TOOLS constant is validated and saved as a pending row, and the loop returns the card. POST /actions/{id}/decision calls decide:

@Transactional
public ToolResult decide(UUID id, User reviewer, boolean approve) {
    PendingAction a = pending.lockById(id).orElseThrow();  // SELECT ... FOR UPDATE
    if (a.status() != PENDING || a.expiredAt(now()) || !a.userId().equals(reviewer.id()))
        throw new ConflictException();                     // HTTP 409
    if (!approve) { a.markDeclined(); return ToolResult.declined(a.callId()); }
    // UPDATE bill ... WHERE id = ? AND version = ?  -- 0 rows: the bill changed
    ToolResult r = tools.run(a.callId(), a.tool(), a.argsJson(), a.expectedVersion());
    if (r.isError()) a.markFailed(); else a.markApproved(reviewer.id(), now());
    return r;                                              // a refusal is a result the model reads
}

The endpoint then appends the result under the model's call id and calls the model again in the same request.

A mature version adds three things:

  • Pause and resume of long runs. A long run saves its program state at the pause; LangGraph and Temporal do this.
  • Edit before approve. The reviewer fixes the amount instead of rejecting, and the edited arguments are validated again before they run.
  • Second reviewers, escalation and timeouts. A different user approves from a queue, and an unanswered card moves to someone else or expires.

Classic analogy: maker-checker (four eyes) in a bank. One clerk enters a payment, a second approves it, and only then does it execute. The model is the maker, the person is the checker, and the pending-action table is the queue between them.

Where it breaks: a human maker is accountable and is not steered by text hidden in an invoice. A model proposes at machine speed, so the checker tires faster.

A reviewer who approves everything protects nothing

Anthropic reports that Claude Code users approve 93% of permission prompts. A card that is almost always right trains the reviewer to click without reading. The fixes:

  • Ask less often: let reads and undoable writes through.
  • Show a diff of each field that changes.
  • Refuse impossible calls before a card is shown, such as marking a bill paid twice.
  • Track the approval rate per tool.

Each reviewer decision is a labelled example you should keep

Every approve, reject and edit grades the model's proposal. Store it with the full prompt the model saw and the version of the fixed instructions, so you can replay it: before changing the prompt or the model, send each stored prompt to the new setup several times, because a model can answer the same prompt differently, and check the proposed arguments still match what the person approved. A rising rejection rate on one tool is an early alarm. Billpod keeps only the answered card's id, for privacy, so it lacks this signal.

Common mistakes

  • Asking the model, in its prompt, to "confirm with the user first". The model can skip it; the check must be in code.
  • Showing the model's own description of the action on the card, or accepting the arguments back from the client on approve.
  • No expiry, no single-use check and no version re-check at execution time.
  • Risky writes the model asks for become proposals. Code runs them only after a person approves, the result goes back under the call's id, and Cancel tells the model it was declined.
  • Code renders the card from stored data. Approving runs exactly the stored arguments, once, before an expiry, for the right user, against the version the card showed.
  • Which tools need approval is a list in code, sorted by risk, so cheap actions do not wear out the reviewer.
  • People approve most prompts. Fewer, clearer cards keep the check real.
  • Reviewer decisions are labelled data about the model's quality, worth storing with enough context to replay.
