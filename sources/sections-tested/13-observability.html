Observability for LLM calls records what the model saw, what it said and what it cost

An LLM call can return a confident wrong answer with HTTP 200, no exception and no log line. Observability for LLM calls keeps one record per call: the exact text sent, the text that came back, the model and prompt version, the token count, the cost and the time taken. On top of those records you sample live traffic, score it, and watch the scores for changes that no deploy of yours explains.

A wrong grade leaves no stack trace

A model (LLM) is a service you send text to and get text back from, run by a provider such as Google or Anthropic. The prompt is the text you send: fixed instructions from a prompt template your team writes, plus the user's data. Each edit of the template is a new prompt version. Providers bill per token, a chunk of three or four characters, in and out.

The running example is a language-learning app in a small codebase of apps. In a translation drill, the learner sees an English sentence and types it in Portuguese. The app sends a model the sentence, the expected answer and the learner's answer, and the model replies with a score from 0 to 100 and a verdict, correct or not.

Made-up incident. On a Tuesday, five learners report the same thing. The expected answer to "I am a barista." is Sou barista.; they wrote Eu sou um barista., which is still correct Portuguese, and it was marked wrong. Nothing has been deployed for a week. The logs show a 1.4-second call that returned 200. You need what they lack: the exact prompt, the exact reply, and which model version answered.

Here the logic is the prompt text plus a model you do not run. The only evidence is the text that went in and came out, and you have it only if you stored it.

LLM calls create five problems that REST calls do not have

  • The bug is in the text: a missing rule, a truncated document, the wrong user's data.
  • Every call has a variable price in tokens.
  • The prompt changes outside a code deploy. Teams often keep templates in a database and edit them without a release.
  • Quality can drift with no deploy of yours. The provider updates the model behind the same name, a provider bug hits, or the inputs change. In a 2023 study, GPT-4 identified prime numbers with 84% accuracy in its March version and 51% in June, under the same API name.
  • Stored prompts contain your users' words, so a store of prompts is a store of personal data.

Classic analogy: distributed tracing plus APM plus a billing meter. The model call is one more timed downstream call, with tokens and cost as extra attributes.

Where it breaks: success is a judgement about the text, not a status code. A model under the same name can answer differently next week. And the payload is usually personal data.

One record per call answers what happened, which version ran, how much and how slow

Every model call goes through one wrapper, which writes one record per call, failed calls included. The record carries the trace ID your tracing library (Micrometer Tracing or OpenTelemetry) gives each request. The wrapper:

  1. Notes the start time and the trace ID.
  2. Records the provider, requested model, template name and version, the feature, and the user it is billed to.
  3. Makes the call and parses the reply into your own result type.
  4. Reads from the reply the model version that actually answered, the token counts and the finish reason: why the model stopped (STOP when done, MAX_TOKENS at the length limit, SAFETY when the provider's filter cut it off).
  5. Computes the cost from a price table. An unknown model gets no cost, so it shows as a gap, not a free call.
  6. Writes the record to the log, and the redacted prompt and reply to a separate table keyed by trace ID.

Tokens come in three kinds: input (the whole prompt), cached input (the part matching the start of a recent prompt, billed at a lower price) and output (the reply).

Made-up record from that Tuesday. The request asks for gemini-flash-latest, a moving alias; the reply names the version that answered.

The smallest useful version is one structured log line per call

Spring AI already emits a Micrometer observation named gen_ai.client.operation for every chat call, with model names, token counts and finish reasons. Prompt and reply text are off by default. You add the feature, prompt version, cost and parsed result yourself. Without Spring AI, a wrapper is enough:

Made-up example: a minimal wrapper in Java

public GradeResult grade(GradeRequest req, long userId) {
    Prompt prompt = prompts.get("translation_grade"); // name, version, text from the DB
    String text = prompt.render(req);
    String traceId = tracer.currentSpan().context().traceId();
    long start = System.nanoTime();
    ModelReply reply = null;
    GradeResult result = null;
    try {
        reply = client.call(MODEL, text);
        result = parse(reply.text());
        return result;
    } finally {
        long latencyMs = (System.nanoTime() - start) / 1_000_000;
        CallRecord rec = CallRecord.of(traceId, "translation_grading", userId,
                prompt, MODEL, reply, result, latencyMs);
        callLog.write(rec.withCost(prices.cost(rec))); // cost null if model unknown
        callText.save(traceId, redactor.scrub(text),
                reply == null ? null : redactor.scrub(reply.text()));
    }
}

callLog.write logs one JSON line. callText.save writes the redacted text to a table kept 14 days and readable only by on-call engineers; that window lets you read the five barista prompts.

OpenTelemetry's GenAI conventions give these fields standard names

OpenTelemetry's GenAI conventions name the span attributes: gen_ai.provider.name, gen_ai.request.model, gen_ai.response.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens, gen_ai.response.finish_reasons, and gen_ai.prompt.version for the template version. Prompt and reply go in gen_ai.input.messages and gen_ai.output.messages, which are opt-in because they are likely to hold personal data. The conventions are still marked "Development", so names can change. Use these names for your log fields too.

Drift is detected by scoring a sample of live traffic every day

Latency and error alerts never fire on drift. An online eval is a check that scores live production calls:

  1. Sample. Send the trace ID to a queue when its hash modulo 100 is below 2: a random 2%. Size the rate per feature to about 200 scored calls a day.
  2. Score, off the request path. A queue consumer reads the call's text and scores it with a deterministic check where one exists. Otherwise a second model, the checker model, judges the answer against a written rubric. Pin the checker to a fixed version. A person can also score.
  3. Store the score keyed by trace ID.
  4. Chart and alert. Chart the daily average per prompt version and per response model. Alert when a day falls below its usual band, for example three standard deviations below the 30-day mean.

Made-up end of the incident. The checker's rubric says a left-out word that keeps the meaning does not make a translation wrong. Its agreement with the verdicts sat between 0.94 and 0.97 for 30 days. On Monday Google moves gemini-flash-latest to a preview version. At 06:00 on Tuesday Monday's rate comes in at 0.81 and fires the alert, hours before the learners write in. Grouping the records by prompt_version and response_model shows "wrong" rising from 4% to 19% on the new model, with prompt version 14 throughout. The team pins request_model to gemini-2.5-flash.

When the reply names no specific version, replay old prompts with known-good answers daily. If they fail too, the model changed. If they pass while live scores fall, your users' inputs changed.

Prompts and replies must be redacted by content before they are stored

Redacting by key name fails here: the personal data sits inside the prose under no sensitive key. Scrub the text itself: patterns catch emails, phone numbers and IBANs, and a detector library such as Microsoft Presidio finds names. my name is Ana Silva, write to ana@example.com becomes my name is <PERSON>, write to <EMAIL>. Keep the text short-lived and restricted; keep the metadata (tokens, cost, versions, scores) longer.

A mature setup adds nested spans, dashboards, feedback and replay

  • Nested spans, one per step, under one trace.
  • Dashboards per feature, prompt version and model.
  • User feedback attached to its trace.
  • Alerts on eval scores and on spend.
  • Replay of stored prompts against a new model before switching.

Common mistakes

  • Logging token counts but not the prompt version, so a quality drop cannot be tied to the edit that caused it.
  • Recording only the requested model name, when the reply names the specific version that changed.
  • Storing full prompts in the normal application log, where retention is long and access is wide.
  • Write one record per model call, failed calls included, with trace ID, feature, user, prompt version, requested and responding model, input, cached and output tokens, finish reason, latency, cost and the parsed result.
  • Store prompt and reply text separately, keyed by trace ID, redacted by content, with short retention and restricted access.
  • Detect drift by scoring a random sample of live calls off the request path, storing the score by trace ID, and charting it per day, prompt version and model with an alert band.
  • Use the OpenTelemetry GenAI attribute names for your fields.
