Governance lets a regulated firm prove what its AI did, on whose authority and on what evidence

Governance is the set of records and controls that let a bank or insurer answer its supervisor's questions about each AI feature: where it is used, how risky it is, what it produced on a given day, who approved it and how it was tested. It exists because the model is a third-party component that nobody in the firm can inspect or reproduce, and that receives client data on every call.

A model differs from a library in four ways that matter here

  • A model provider such as OpenAI or Google runs the model behind an HTTP API, so client data goes to their servers.
  • Fixed snapshots such as gpt-4o-2024-08-06 sit next to aliases such as gpt-4o that move to newer builds, like a Docker tag latest. Pinning means always calling the snapshot.
  • The model picks words with some randomness, so the same input can give a different text, and it can state things not in its input.
  • The prompt is the text your code sends: fixed instructions from your team plus the case data.

A use case is one business purpose for calling a model.

An auditor's questions show what a normal backend cannot answer

Made-up running example. A Swiss private bank transcribes client calls. After a call, the client's adviser presses a button, and the advisory-notes service sends the transcript to a model, which drafts the meeting note, including the client's risk appetite. The adviser edits and saves it. Fourteen months later a client complains that a risky product was sold against their wishes. Internal audit asks:

  1. Which model wrote the draft of the note from 12 March, and with which instructions?
  2. What did the draft say before the adviser edited it?
  3. Where did the transcript go, and does the provider still hold a copy?
  4. How was the feature tested before it went live, and who signed it off?
  5. How do you know it still worked as tested in March?

For a classic Spring service, git, the change ticket and the database answer these. Here git does not hold the model, the alias may have moved, a rerun gives a different draft, the draft was never stored, and nobody checked the provider's retention terms.

FINMA applies its existing rules and checks seven areas

Switzerland has no AI-specific law. FINMA Guidance 08/2024 (18 December 2024) says the existing governance and risk-management rules cover AI, and lists seven areas it checked. Each maps to an engineering artefact:

GovernanceA named owner per use case; the provider contract on file

Independent reviewSign-off by someone outside the building team

The inventory gives each use case a risk class, and the class decides the controls

The inventory has one row per use case: the owner, the data sent, the pinned snapshot and its retirement date, the provider region and retention option, the service credentials allowed to use it, and a risk class. FINMA's proportionality factors (client impact, financial impact, whether a person checks the output) become a firm rule. Made-up example:

  • High if the output reaches or decides about a client unchecked. Adds zero retention at the provider and a named approver per output.
  • Medium if client data is sent but an employee corrects every output. Adds a European region, evals and weekly monitoring.
  • Low if no client data is sent. Needs the row, the audit record and the provider contract.

The meeting note is Medium. To keep the inventory complete, route every call through a gateway: an internal service that alone holds the provider keys. A caller authenticates with its service credential and sends the use-case id, the prompt version and the logged-in user. The gateway refuses the call if no row matches that use case and credential, takes the snapshot and region from the row, and returns a call_id with the draft.

Every call writes an audit record that stores the output, because it cannot be produced again

A small codebase of apps stamps each model-written lesson note with its configured model name and a prompt version:

apps/tunatutor/backend/src/services/tutor-continuity/lesson-note-writer.ts:224-225

        writerModel: deps.model,
        writerPromptVersion: LESSON_NOTE_PROMPT_VERSION,

For a bank that has two gaps: the name is what the app asked for, not the build the provider ran, and a later write overwrites the model's original.

The gateway closes both. It records the version the provider reports in its response: OpenAI's model field, Gemini's modelVersion. The prompt version is the id of the instruction file in git, such as meeting-note/v7. The full prompt and draft go to an encrypted, access-controlled content store; the audit tables hold pointers. The tables take INSERT only: edits, approvals and deletions are later event rows keyed by call_id.

Residency and retention are provider terms that you check and record per risk class

Take OpenAI. Abuse-monitoring logs are kept "for up to 30 days" by default. Zero Data Retention is "subject to prior approval by OpenAI". A project can use the region "Europe (EEA + Switzerland)", which does not promise Switzerland. So question 3 is answered from the inventory row, which records the region and retention option.

The provider is outsourcing, managed by the third-party risk process with an exit plan: a second provider or snapshot with its own passing eval.

Eval reports are the validation evidence, and monitoring keeps them true

An eval is a test run over a fixed set of cases that produces a score against a pass bar agreed in advance. Here, 300 past transcripts. Free text is scored by:

  • Code checks: every figure in the draft appears in the transcript.
  • A grader model: a second model call with a yes/no question, such as "does the draft state a risk appetite the client did not say?". It is first calibrated against 50 human labels.
  • Human reviewers score a sample.

Made-up result: 1 invented risk appetite in 300 drafts, against a 1% bar. Rerun it when either changes, including a one-word prompt edit. An alias would let the provider swap the validated model.

After go-live, a weekly job scores a sample of live calls against the same bar and tracks the edit rate (draft versus final text) against a threshold.

A named person signs off, and high-risk outputs wait for a human

Before release, someone outside the building team reads the model card (one page: purpose, model, prompt version, eval result, limits, fallback) and eval report, and approves the change ticket. At run time, for the High class only, the feature saves the output as PENDING, like a payment waiting for a second signature. A named approver releases it, which adds an approved event row.

NIST and the EU AI Act ask for the same artefacts

The voluntary US NIST AI Risk Management Framework has four functions: Govern, Map, Measure and Manage, and a GenAI Profile, NIST AI 600-1. The EU AI Act makes credit scoring and life or health insurance pricing high-risk, with those duties applying from 2 December 2027.

The smallest version fits in a sprint, and a mature version adds independence

Smallest version: an inventory table; a gateway that refuses unregistered calls; insert-only audit tables and a content store; provider terms and exit plan on file; an eval report and model card per change ticket.

Mature version: a registry audit can browse; monitoring that opens reviews itself; an independent validation team; periodic provider reviews.

The classic backend analogy. This is the bank's change process plus vendor due diligence plus its existing model validation for credit scoring.

Where it breaks. The change process assumes nothing changes without a deployment, and model validation assumes you can inspect and reproduce the model. Neither holds, so you test from outside with evals and keep every output. And part of the specification is a plain-language prompt, so a one-word edit needs the same review as code.

Common mistakes

  • Overwriting the draft. Saving the edited note over the draft destroys the answer to question 2.
  • Validating against an alias. The eval passed on last quarter's model, and production now runs a newer one under the same name.
  • Assuming the provider keeps nothing. Default terms keep abuse-monitoring logs; zero retention needs approval.
  • One inventory row per use case, with owner, risk class and credentials; the gateway refuses calls without one.
  • Each call writes an insert-only row with the reported model and prompt versions and stores the draft; edits are new event rows.
  • Region and retention are provider terms recorded per risk class, managed as outsourcing.
  • Eval reports tied to a pinned snapshot and prompt version are the evidence; rerun on any change.
  • High-risk outputs wait for a named approver; releases need an outside reviewer.
