Context engineering decides what the model sees on every call

A language model answers only from the text sent to it in one request, and that text has a hard size limit. Context engineering is the server code that chooses, orders and trims that text for every call. It exists because the model keeps no state between calls, and because a request that is too full gives worse answers as well as costing more.

The model remembers nothing between two calls

The running example is Ask Billpod, a chat panel in a household-bills app from a small codebase of apps that this guide quotes. A person types two messages:

  1. "Did we pay the electricity bill this month?"
  2. "Mark it paid, by e-banking."

Billpod answers each message by calling a large language model (LLM): a remote service that takes text in and returns text out over an HTTP API. The model has no session. It cannot know what "it" means in the second message unless that request also contains the first question and its answer.

So the browser keeps the conversation and sends it with every new message, and the server rebuilds the whole model request each time.

Tokens measure the request, and the window caps it

A token is the unit a model reads and bills by, roughly four characters of English. The context window is the most tokens one request can hold, counting the input and the answer the model writes. Current models allow 200,000 to about 1,000,000 tokens. The limit is enforced: Anthropic's API rejects an input over it with HTTP 400 "prompt is too long". Because the answer counts too, each request also sets maxTokens, the most tokens the model may write; Billpod sets 2,048. A reply that reaches that cap stops mid-sentence.

Each request is assembled from five layers

A model request carries three fields of content. The system prompt holds the developer's instructions for the whole conversation. The tool definitions describe functions the model may ask the server to run: a name, a description in plain words, and a JSON Schema for the arguments. The messages are a list, each with a role: user for the person, assistant for the model, and tool for data the server sends back. Billpod fills five layers into these fields, fresh for every message:

One answer can take several model calls. Made-up values in Billpod's real request shape. The server's first request for "Mark it paid, by e-banking.":

{
  "systemPrompt": "You are Ask Billpod ... Today is Tuesday, 2026-10-13 ...",
  "tools": [ { "name": "find_bills", ... }, { "name": "mark_paid", ... }, ... ],
  "messages": [
    { "role": "user",      "content": "Did we pay the electricity bill this month?" },
    { "role": "assistant", "content": "Not yet. The electricity bill, 84.20 CHF, is due on 20 October." },
    { "role": "user",      "content": "Mark it paid, by e-banking." }
  ],
  "maxTokens": 2048
}
  1. Call 1. The model replies with text plus a list of tool calls, each with an id. Here it asks for find_bills {"text": "electricity"}, because the history kept only the earlier answer's text.
  2. Call 2. The server runs the calls in order, appends the calls and their matching results to the messages, and calls the model again. Errors go back as results too. Now the model asks for mark_paid on bill b_19.
  3. A pause for the person. Only the writes on a fixed list, such as mark_paid, wait for the person's approval; reads and plain additions run at once. The server sends the browser a sealed approval ticket, which it can neither read nor change, holding the calls so far and the exact mark_paid call.
  4. Call 3. On approval the browser sends the ticket back. The server runs the sealed call and calls the model once more; nothing is re-run. The model replies "Done" with an empty list of tool calls, which ends the loop.

The rule: call the model, run the tools it asks for, append calls and results, and stop when the list is empty. Billpod caps this at 6 model calls per answer.

The history is cut to a budget, newest message first

Billpod keeps the newest history that fits 24,000 characters, roughly 6,000 tokens. The system prompt and tools are counted outside that budget. Earlier answers' tool calls and results are left out; each earlier write keeps only a one-line note of its outcome, such as mark_paid (electricity): done. The trimming walks backwards from the newest message:

apps/billpod/backend/src/ai/assistant/history.ts:36-45 (simplified)

  let used = 0;
  let from = rendered.length;
  for (let i = rendered.length - 1; i >= 0; i--) {
    const cost = rendered[i].content.length;
    // The newest message (the person's question) is always kept.
    if (i < rendered.length - 1 && used + cost > budget) break;
    used += cost;
    from = i;
  }
  while (from < rendered.length - 1 && rendered[from].role !== "user") from++;

Three rules follow. The newest message always survives. Older messages are dropped whole, never cut in the middle. The kept slice starts on a user message, because model APIs expect the roles to alternate, starting with the person.

Billpod counts characters instead of tokens because that is free. The margin below the window absorbs the estimate's error.

A fuller window gives less reliable answers

In a 2025 study by Chroma, 18 models answered the same questions about a long chat twice: once from the full history of about 113,000 tokens, once from only the relevant part, about 300 tokens. Every model answered more questions correctly from the short version. Passages that looked relevant but were not, called distractors, hurt the most. This is context rot: a fuller window gives less reliable answers. So the budget limits quality as well as size and cost.

Load data when a question needs it

Billpod sends none of the household's bills up front. Its system prompt says: "Use the tools for every fact. Never guess an amount, a date, or whether something is paid." Old tool results are not replayed, because household data changes; that is why the model called find_bills again in Call 1. Anthropic calls this just-in-time loading: keep small references such as an id in the window and fetch the content with a tool when needed.

Long-running agents compact, clear and delegate

An agent calls tools in a loop for many steps, so its window fills much faster. Billpod uses none of the following; they come from Anthropic's write-up on context engineering:

  • Compaction. When the window is nearly full, ask the model to summarise the conversation so far, and send that summary in place of the history from then on.
  • Clearing old tool results. Replace the output of a tool called many steps ago with a short placeholder.
  • Notes outside the window. The agent writes progress to a file and reads it back later.
  • Sub-agents. A separate model conversation with its own empty window does a search and returns only a summary, "often 1,000-2,000 tokens".

The smallest version fits in one class

The minimum is what Billpod does: one assembler that builds the five layers, with history trimmed to a budget, and runs the tool loop with a step cap. A mature version adds:

  • a log of every assembled request, so a wrong answer can be traced to what the model saw;
  • real token counts from the provider instead of a character estimate;
  • a separate budget for each layer, with a rule for which layer is cut first.

Classic backend analogy. Context assembly is a response assembler that builds one DTO under a hard payload limit. The system prompt is the static part, the history is a paged query sorted newest first, and tool calls are lazy loading: fetch the association only when it is accessed.

Where it breaks. A DTO consumer reads every field the same way. A model reads free text: the order and wording of the layers change its behaviour, and a correct but irrelevant field makes its answer worse. And nothing raises an error when something important was trimmed. The model answers anyway, from what is left.

Common mistakes come from treating the window like a payload

  • Sending everything because it fits. Context rot and cost start long before the window is full.
  • Forgetting facts the model cannot know, such as today's date, timezone and language.
  • Replaying old tool results, which waste tokens and can contradict current data.
  • The model is stateless: every call must carry everything it needs.
  • The context window is a hard token limit for input plus output, and answer quality drops well before it is reached.
  • Build each request in one assembler from layers: system prompt, tool definitions, trimmed history, the new message, and this answer's tool calls and results.
  • Fetch data with tools when a question needs it, and do not replay old tool results.
  • Long agent runs also need compaction, cleared tool results, notes outside the window and sub-agents.
