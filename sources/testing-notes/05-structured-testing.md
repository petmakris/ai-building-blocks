# Testing notes from the first workflow

## Key points

- The problem is new to backends: a model answers in free text, and asking for JSON in the prompt alone fails in five ways. The JSON comes wrapped in a code fence or a sentence, the syntax is broken, the reply is cut off at max tokens, the reply is a refusal that still returns HTTP 200, or the JSON is valid but holds a wrong or invented value.
- You send a JSON Schema with the request: Gemini's generationConfig.responseSchema (an OpenAPI 3.0 subset), or Anthropic's output_config.format (standard JSON Schema, with the reply in content[0].text). The provider then uses constrained decoding: at each token it removes the candidates that would break the grammar compiled from the schema. A reply that finished normally therefore parses, holds only the declared fields with their declared types, and holds every required field. Fields not listed as required may be left out or sent as null. Both mean 'not stated', and Billpod keeps every field optional so the model is not pushed to invent one.
- Constrained decoding guarantees the shape only. Providers reject or drop some rules: Anthropic rejects minimum, maximum, minLength, maxLength and recursive schemas, and Lomem drops bounds and patterns before sending a schema to Gemini. A refused or cut-off reply can ignore the schema. The values are still the model's guess.
- Treat every reply like an untrusted request body (OWASP LLM05), in three layers. First read the finish reason: STOP/end_turn, MAX_TOKENS/max_tokens (often caused by Gemini 2.5 thinking tokens; raise the cap once, then fall back), SAFETY etc./refusal, or a blocked prompt. Then check that the whole answer is usable: it parses, it is an object, each field has the right type. A failure here rejects the answer, so keep this layer to those rules. Then check each value against the domain: real dates, the IBAN checksum, ISO currency codes, length limits, control and bidi characters stripped. A field that fails is dropped, never guessed.
- Text inside the document can steer the model (prompt injection), and a valid IBAN from an attacker passes every check. Billpod lets fields read exactly from the QR code win over the model's reading, records each field's source, and has a person confirm every draft.
- Retry a bounded number of times when the whole answer is unusable, putting the validation error in the next prompt. The model sees only that error, not its earlier answer. Do not retry a refusal. Drop individual failing fields instead of retrying when a person reviews anyway. End in a defined fallback: Billpod does not retry at all and falls back to a draft read from the QR code only, and the reading is always a draft that a person confirms.
- A mature version generates the provider schema and the local validator from one definition (in Java, Spring AI's BeanOutputConverter and .entity(Record.class)). It also asks the model for a self-rated confidence per field, used only to order the human review, and logs each failure by kind.
- The analogy is Jackson plus Bean Validation on a DTO from an external partner's API. It breaks in five places: the answers are nondeterministic, a 200 can be a refusal, a body that passes validation can still be invented, a wrong answer still costs money, and a third party (the document's author) writes part of the content.
