# Testing notes from the first workflow

## Key points

- The model is billed per token and keeps no state between calls, so every request resends a long fixed opening: tools, system prompt and history. Provider prompt caching reuses the provider's computation for an exact prefix, and the cache is per model. Output is never cached. Per Anthropic's docs: the prefix order is tools, system, messages. You mark the end of a prefix with cache_control on a tool, a system block or a message content block. Each of up to 4 markers is its own cached prefix, and "ttl": "1h" is optional. A write costs 1.25x the input price (2x for 1 hour), even if never read, and a read costs 0.1x. An entry lasts 5 minutes and is renewed on each hit by any user. A prefix under the model's minimum (512-4096 tokens) is not cached, and no error says so. Caches are isolated per organization and workspace. OpenAI caches automatically from 1,024 tokens.
- Put stable content first and variable content last, and do not mark text that changes on every call. A timestamp near the top, or tools listed in an unstable order, drops the hit rate to zero. In a chat, the marker goes on the newest message and moves every turn. Verify with cache_read_input_tokens, cache_creation_input_tokens and input_tokens. The share read / (read + creation + input) is token-weighted, so it peaks below 1, at prefix / (prefix + tail). One reuse within 5 minutes pays for a write (1.35 vs 2), so caching loses money only when most calls arrive alone, more than 5 minutes apart. The 1-hour lifetime pays when the first call is followed by at least two more within the hour.
- An exact response cache skips the model call entirely, like Spring @Cacheable on Redis. The flow is: normalise, look up, on a miss call the model (prompt-cached), validate, upsert. Key it on normalised input plus the language or tenant, and normalise only as far as meaning allows. A shared cache must hold no personal data. Model output is not deterministic, even at temperature 0, so the cache freezes one answer for every user. Validate before storing, and let users report and evict a bad answer. When two misses arrive at once, both call the model and the upsert keeps the last answer.
- Invalidate by version. Stamp each row with a version number from a code constant and compare it on read. Treat older rows as misses so they regenerate lazily on their next read, with no expiry or migration job needed. Bump the version in the same commit that changes the prompt, the output schema or the model. The key or version must cover everything that changes the answer, including call parameters. During a rolling deploy, a write should not overwrite a row with a higher version.
- A semantic cache matches questions by embedding similarity (cosine, roughly 0 to 1, with a threshold). It can return a fluent wrong answer ('cancel a card payment' served for 'cancel a card') or leak one user's data to another. Use it only for low-harm content with no personal data, scope it per tenant, set the threshold from labelled question pairs (and skip it if none separates them), and log each hit with the question it matched.
- The smallest useful version has two steps. First, order prompts stable-first, add a cache_control marker and log the three input token counts. Second, add an exact cache for common questions that carry no personal content, with a version in each row that is compared on read. A mature version adds a hit-rate dashboard, the 1-hour lifetime for sparse traffic, pre-warming, a report button that evicts bad answers, and a tenant-scoped semantic cache only where it pays.
