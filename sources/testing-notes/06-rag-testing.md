# Testing notes from the first workflow

## Key points

- The section is at sources/sections-tested/06-rag.html. It is about 3,300 words of prose plus code and tables, at the 3-page limit. Lomem has no retrieval code, so the running payments example (PAY-4012) is made up and labelled as such. The figures come from Anthropic's Contextual Retrieval post, the pgvector README and Voyage AI's docs. The Postgres full-text query was run on PostgreSQL 18.
- A model knows nothing about your data and keeps nothing between requests. RAG is a search step that your code runs before the model call. Offline, it chunks, embeds and stores each document with doc_url and access_groups. Per request, it embeds the question, searches for the best chunks the caller may read, fetches their text, and pastes them in numbered, under instructions to cite them and to say 'I don't know' when the answer is missing. It then sends the result as one Messages API call (one user message, max_tokens caps only the answer), turns each [n] into a link and flags any answer that has no citation.
- An embedding is a fixed-dimension vector computed over HTTP by a separate embedding model. Cosine similarity is shown with its formula and a worked 3-number example. The score ranges from -1 to 1, but unrelated real texts score about 0.2-0.4, so read it as a ranking. Each model has its own coordinate system: the model fixes the vector(n) dimension, and changing the model or the chunking means re-embedding everything. The question uses the same model with input_type 'query', and chunks use 'document'.
- Chunking decides what one search hit is. Split on structure (headings, one chunk per ticket comment), count tokens as characters divided by 4, and split anything over about 500 tokens. A chunk without context, such as 'Restarted the clearing adapter, fixed', cannot be found. Contextual chunks prepend an LLM-written line that is stored in body, so it is embedded, keyword-indexed and shown to the model. Prompt caching makes this cost about $1.02 per million document tokens in Anthropic's setup.
- Keyword search (BM25) and vector search fail on different questions: exact codes like PAY-4012 against paraphrases. Postgres full-text search with the 'simple' config works as the keyword side once websearch_to_tsquery's AND is turned into OR. RRF, 1/(60 + rank), merges two lists of about 50 in a few lines of Java, followed by one query that fetches the bodies by id. A reranker scores each candidate together with the question, from 150 down to 20 in Anthropic's setup. Put 5 chunks in the prompt without a reranker and 20 with one, because extra chunks bring in near-misses.
- Access rights are read from the source's permission API at indexing time and filtered inside the search query (access_groups && callerGroups). There are three traps. Filtering after the top-K cut can leave nothing. pgvector applies WHERE after the hnsw scan of ef_search=40 candidates, so a strict filter returns too few rows unless hnsw.iterative_scan is set (pgvector 0.8.0+), ef_search is raised, or a partial index is used. Copied permissions go stale unless a permission change triggers re-indexing (delete by doc_url, then re-insert), driven by webhooks or polling.
- Retrieval is measured on its own, without calling the model, with recall@k over real questions labelled by document URL. Each chunk is mapped to its doc_url, and k is the number of chunks in the prompt. In Anthropic's numbers the top-20 failure rate fell from 5.7% to 3.7%, 2.9% and then 1.9%, which is 67% fewer failures. The analogy is Elasticsearch fed by CDC with per-user filtering. It breaks in three places: the model builds an answer on bad hits, relevance is measured statistically, and retrieved text can carry prompt injection, which has its own short subsection.

## Fact-check

- fixed: Full-text search paragraph: the old text said the 'simple' configuration keeps codes 'as typed'. That was wrong. I ran the query on PostgreSQL 18 (lomem-studios-postgres container) and to_tsvector/websearch_to_tsquery split PAY-4012 into the phrase 'pay' <-> '-4012'. The text now says this, and that the phrase still matches only that exact code.
- fixed: Contextual chunks: the old text said Anthropic's post 'names the fix contextual chunks'. The post actually uses 'Contextual Embeddings' and 'contextualized chunks'. The text now says the post calls them contextualized chunks and this section calls them contextual chunks.
- fixed: Prompt caching: the old text said a cache hit costs 'a tenth of the price'. It now says 'a tenth of the input price at Anthropic (less on some newer models)'. The pricing page lists 0.1x as standard, but 0.05x for Opus/Sonnet 5.5 and 0.025x for Fable/Mythos 5.1.
- unverified: The section has no Lomem code excerpts with p.src path:line, so there was nothing to compare against ~/projects/lomem.
- unverified: The constant k=60 in RRF coming from the original paper (Cormack, Clarke, Buettcher 2009): this is well-known but was not fetched, and the section does not link the paper.
- unverified: Jira sending a webhook when an issue's security level changes: assumed to arrive as issue_updated, not checked against the docs. Confluence's content_permissions_updated event was checked, in the Confluence Data Center docs. A Jira bug report (CONFCLOUD-82583) says Confluence Cloud's Forge permissions_updated event can fail to fire when a page restriction is added.
- unverified: The tokens ≈ 4 characters rule, the 'few hundred thousand' context window and the '768 to 3,072' embedding dimension range are general rules of thumb with no source cited.
- unverified: The example uses claude-sonnet-4-5, which is still a valid model id, but the pricing page now marks Claude Sonnet 4.5 as deprecated. I left it unchanged.
