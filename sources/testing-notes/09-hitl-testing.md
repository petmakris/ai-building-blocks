# Testing notes from the first workflow

## Key points

- When a model asks to run a risky write, the system turns the request into a proposal and ends the turn. A person sees a confirmation card and clicks Approve, which is a new request, and only then does code run it. The result goes back to the model under its own call id. Cancel tells the model the person declined.
- This problem is new to classic backends. The model is a caller that can be confidently wrong, and text it reads (an invoice, a payee name) can steer it, which is prompt injection. Instructions and filters reduce injection, and the approval click is what stops that text from changing data on its own. MCP, the open standard Billpod also uses to offer its tools to outside assistants, requires consent before any tool runs.
- The pending action must be tamper-proof. Code renders the card from the stored record plus the call's checked arguments, never from the model's own description. Approving runs exactly the stored arguments, once, before an expiry, for the right user, with the record's version checked again when it runs (optimistic locking). A version refusal goes back to the model, and the card is used up. The client sends only a reference and the decision. A database row is the usual design. Billpod stores no conversations on the server, so it uses an AES-256-GCM sealed token instead. The token carries the call and the turn's earlier steps and is bound to the user, household and a hash of the chat. It also has a 10-minute TTL, a single-use row written only on answer, and a version check.
- Each tool's risk level decides whether it needs approval, and the list lives in code, never in the prompt. Billpod runs reads at once. It runs add-only writes at once, with an Undo for an added bill that deletes it at its created version. It stops edits, deletes and mark_paid at a card. Later writes in the same model step are answered 'not run', sent with the decided result after the click, because they may depend on the unapproved change. Reads in that step still run. A mature system adds levels by amount and a second reviewer.
- The smallest version is a pending-action table, a stored conversation and a decision endpoint. The endpoint locks the row and checks status, expiry and who may approve. It then runs the stored arguments with an optimistic version check, marks the row approved or failed, appends the result and calls the model again. A mature version adds three things: saved program state so a long run can pause and resume (LangGraph, Temporal), an edit step before approval with the edit validated again, and second reviewers, escalation and timeouts.
- Rubber-stamping is the main failure. Anthropic reports that Claude Code users approve 93% of permission prompts. The fixes: ask less often, show diffs, refuse impossible calls before a card is shown, and track the approval rate per tool.
- Every approve, reject or edit is a labelled example of the model's quality. Store it with enough context to replay it: the full prompt and the instruction version. Replay it several times as a test before changing the prompt or the model, and use it for early alarms. Billpod keeps only the answered card's id, for privacy, so that signal is not available there.
