# Testing notes from the first workflow

## Key points

- Code that an agent writes and runs at request time is untrusted. The model cannot tell your instructions apart from instructions hidden in the data it reads (prompt injection), and no review can confirm the code is safe before it runs. The defence is therefore that unsafe code cannot do damage. An input filter helps as a first layer, but it cannot be the only layer.
- Isolate both the filesystem and the network, because each fails alone. With only filesystem isolation, the code can still send the files it was given (the CSV) to the internet. With only network isolation, the code can read secrets and write a file (a result file that gets exported, a shared folder, or ~/.bashrc and a build script on a laptop) that something or someone outside the sandbox later runs or copies out. Claude Code's built-in sandbox is one product's example: writes go only to the working directory and a temp directory, and all traffic goes through a proxy whose domain allowlist starts empty. Reads are still broad, including ~/.ssh, until denyRead (with allowRead carving exceptions) is added to its settings.
- Credentials stay outside the sandbox. The code inside sees a placeholder, and the egress proxy decrypts the request (TLS termination, which needs the sandbox to trust the proxy's certificate) and swaps in the real token only on requests to that token's own host. Masking stops theft but not misuse against that host, so keep the token's scope minimal and let the proxy refuse methods the task does not need. Claude Code offers this as credentials mode 'mask' with injectHosts.
- There are three strengths of boundary. An OS sandbox (bubblewrap or Seatbelt) and a container share the host kernel, so they are about equally strong, and one kernel bug lets code out. A microVM (Firecracker) has its own kernel, boots in under 125 ms and has under 5 MiB of overhead, so hosted agent sandboxes give each session its own VM. A locked-down container is a reasonable start for hosts that serve your own staff, even with client-written input. Strangers or many customers on shared hosts need microVMs.
- Every run needs limits on CPU, memory, process count, wall-clock time (an inner timeout plus an outer kill by the runner) and output size. They stop code that is merely wrong, such as a runaway loop or a huge stack trace that would fill the model's context window. The model should be told the exit code and the reason (124 timed out, 137 killed for memory) so it can retry.
- The smallest version is a fresh locked-down container per run, built from an image that already holds its packages: --network none, a read-only root filesystem, read-only input and code, one writable output folder owned by the sandbox user, no secrets, not root (user nobody, all capabilities dropped, no-new-privileges), and a timeout. It is started by a small separate runner service, because access to the Docker daemon's socket equals root on the host. On Kubernetes, use one Pod per run instead. A mature version adds a microVM per session, an allowlist proxy on an internal network so it is the only way out, credential injection at that proxy, and a log of blocked connections.
- An analyst sandbox is a long-lived session, like a Jupyter kernel that keeps variables between cells. Each cell gets a timeout (interrupt, not kill), the memory, CPU and process limits cover the container, and the session has its own cap. It gets a read-only copy of the data, never a live database connection with write rights, and an allowlist that holds only the package mirror. Output leaves only as files that are reviewed like any export, by a person or a DLP scanner. The sandbox is deleted when the session ends.
