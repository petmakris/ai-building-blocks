# Testing notes from the first workflow

## Key points

- The model never runs anything. It replies with a structured request, a Gemini functionCall {name, args}. Your code validates it and runs it. The model API is stateless, so the next call resends the system instruction and the whole conversation, including the model's functionCall and your functionResponse (under role user). The agent loop repeats this until the reply holds no function call. A hard cap applies: Billpod allows 6 model calls per message, including the model's retries after a tool error.
- A tool definition is two things at once. It is a technical contract: a name and a zod or JSON Schema input. It is also instructions the model reads: the description and .describe() text say where ids come from (find_bills before mark_paid), which formats to use and what is refused. The schema is only a request to the model, so the server validates every call again.
- One runner, runTool, takes the tool, the arguments and a context (user, household, scopes). It checks scopes, then the input, then runs the handler, then checks the result shape if the tool declares one. It always returns {ok:true,data} or {ok:false,error}, and that object is what the model receives. A tool is a thin adapter over the same service layer the REST API uses and never bypasses it.
- Errors are written for the model to act on. A stale-version conflict names the tool to re-read with and says to retry. A missing scope says 'Tell the person; do not retry.' Internal failures hide behind one generic message, and the real error goes to the log.
- Writes the person must approve stop the loop at a confirmation card. Billpod's in-app assistant uses an explicit list of tools for this, not the annotation. The arguments are validated before the card shows. The pending call, the conversation and the step count travel through the browser as an encrypted, tamper-proof token that expires after 10 minutes. Approve runs exactly those arguments and continues with the saved step count. Reject sends the model a 'declined, do not propose again' result.
- MCP is JSON-RPC 2.0 over HTTP: initialize, tools/list and tools/call at POST /mcp. Outside assistants such as Claude use it to call the same tool catalogue through the same runner. Results come back as typed content parts, with isError for failures. The client runs the loop and keeps the conversation, so Billpod's server stores no conversation, and Billpod's cap and card do not apply. The initialize reply carries plain-language instructions that add to the tool descriptions.
- OAuth 2.1 decides what an outside assistant may do. The steps are discovery documents (RFC 9728, RFC 8414), dynamic client registration, consent, then a code exchange with PKCE (S256 only). The resulting tokens are bound to the /mcp resource and the granted scopes. A read-only grant stops mark_paid with 403 insufficient_scope. Annotations (readOnly, destructive and idempotent hints) tell clients about side effects. Hints from servers you do not control are untrusted.
- Text inside the data a tool returns can steer the model. This is prompt injection. The real defences are scopes, confirmation and service rules, because a sentence in a prompt guarantees nothing.
- The classic analogy is a REST endpoint with OpenAPI, a controller with validation, and MCP working like JDBC. The analogy breaks because the caller picks endpoints from a sentence, acts on error text and can be steered by data it reads. The common mistakes are trusting arguments, one tool per table, raw exceptions, over-privileged runners, skipping the services, and huge results that cost tokens and fill the context window.

## Fact-check

- fixed: Call 1 example: the JSON Schema type values are now upper-case (OBJECT, STRING, INTEGER). Billpod's converter (packages/shared/src/tools/gemini.ts) sends them that way to Gemini.
- fixed: Call 2 example: the functionResponse payload is now {"result": {...}}, not {"ok": true, "data": ...}. The in-app assistant wraps results with toolResponse() in assistant.ts:196, as {result} on success and {error} on failure.
- fixed: Gemini call matching: the paragraph said Gemini matches results 'by tool name and position'. Google's generateContent function-calling page says Gemini 3 returns an id with every functionCall and that the id should be sent back. The paragraph now says Billpod sends back only the name and Gemini matches by name. It also says Billpod keeps each call's id and makes one up when Gemini sends none (gemini.ts:682).
- fixed: Runner paragraph: 'that object is what the model receives' is now 'the in-app assistant hands the model data as result, or the error object as error'.
- fixed: ASSISTANT_CONFIRM_TOOLS list: attach_link added (packages/billpod-shared/src/ai/assistant.ts:108-110).
- fixed: Confirmation card: 'The server keeps no row' was false. Production uses prismaConfirmationLedger (index.ts:409), which stores the id of each answered card until the token expires, so a card can be answered only once. The text now says that nothing is stored for a card nobody answers.
