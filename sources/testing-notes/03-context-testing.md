# Testing notes from the first workflow

## Key points

- The model is stateless: it keeps no session, so every call must carry everything it needs. Ask Billpod's browser holds the conversation and sends it back with each message, and the server rebuilds the whole request every time.
- A token is the unit a model reads and bills by, roughly four characters of English. The context window is the hard token limit for one request, counting input plus output: 200k to about 1M tokens on current models. Anthropic's API rejects input over the limit with HTTP 400 'prompt is too long'. maxTokens caps the output part (Billpod: 2,048), and a reply that reaches it stops mid-sentence.
- Each request is assembled in one place from five layers that map onto three API fields. The system prompt carries facts the model cannot know, such as today's date, timezone and language. The tool definitions give a name, a description and a JSON Schema. The messages list holds history trimmed to a budget, the new message, and this answer's tool calls and results, each with a role: user, assistant or tool.
- One answer can take several model calls. The model replies with text plus a list of tool calls (each with an id). The server runs them in order, appends the calls and the matching results (errors included), and calls the model again. This repeats until the list is empty, with a cap of 6 steps in Billpod. Only the writes on a fixed list, such as mark_paid, pause for the person's approval, and the state so far is carried in a sealed approval ticket so that nothing is re-run. Reads and plain additions run at once.
- Billpod keeps the newest history that fits 24,000 characters, with the system prompt and tools counted outside that budget. It drops whole messages, starts on a person's message, and leaves out earlier tool calls and results, keeping only a one-line note of each earlier write's outcome. It counts characters because that is free, and the margin below the window absorbs the estimate's error.
- Context rot means a fuller window gives less reliable answers. In Chroma's study of 18 models, every model answered more questions correctly from a focused ~300-token prompt than from the full ~113k-token history, and distractors hurt the most. So the budget limits quality as well as size and cost.
- Just-in-time loading means fetching data with tools when a question needs it, not sending it up front. Billpod's prompt says 'Use the tools for every fact', and it does not replay old tool results, because the household data may have changed.
- Long-running agents need more: compaction (summarise near the limit and send the summary in place of the history from then on), clearing old tool results, notes kept outside the window, and sub-agents that return summaries of 1,000-2,000 tokens. Lomem uses none of these, so this part cites Anthropic.
- Analogy: a DTO or response assembler under a payload limit, where the history is a paged query and tools are lazy loading. The analogy breaks in three places: order and wording change behaviour, irrelevant but correct data makes answers worse, and nothing raises an error when something important was trimmed.
