# Testing notes from the first workflow

## Key points

- An eval runs an LLM feature over many fixed real inputs, scores each output and compares the pass rate to a bar set before the run. assertEquals fails because the output varies from run to run (temperature, and not even 0 makes it fully deterministic), is open-ended (free-text explanations), and one case proves nothing.
- An eval has three parts. The dataset is real traffic plus a hand-made golden set of inputs whose answers an expert decided, each tagged with the kind of case it tests. The scorer decides each case. The bar is a numeric threshold, one per check, written down before the run and never lowered after a miss. It comes from the old version's score, or for a new feature from a cheap baseline or the cost of an error. Real rows with no human answer use the old version's verdict as the reference. That measures change, so a disagreement may be a fix: a person reads every disagreement, and real fixes get a human answer and move into the golden set, where they are scored against it. Correctness comes from the golden rows.
- Scorers are used cheapest first: exact match for labels, then code assertions (valid structure, the word exists, reply under 2.5 s), and an LLM-as-judge with a written rubric only for what code cannot check. An LLM judge is a separate model call from the feature. It is trusted only after it has been compared with human labels on both passes and fails (true positive and true negative rate).
- Error analysis comes first: read 30-100 real outputs by hand, note each failure and group the notes into categories. Each category becomes golden rows with its own failure count, plus a check of its own when code can test it, as the note column in Lomem's fixture shows. Keep separate checks separate, so a slow right answer is not counted as a wrong one.
- A regression eval reproduces a fixed bug. The regression set must stay near 100% (a two-case check is all-or-nothing) and blocks a change. It belongs in the pipeline when the cost of model calls is accepted (Lomem runs it by hand for cost). A capability eval measures what does not work yet, blocks nothing, and graduates its cases into the regression set. Pair negatives with positives so 'reject everything' cannot pass.
- A pass rate is an estimate of the true rate (the rate over all inputs users will send). The standard error √(p(1−p)/n) is how far the estimate typically lies from it: two standard errors is about 3 percentage points at 200 cases and about 7 at 40. Model randomness adds a smaller run-to-run wobble. Compare prompts on the same rows, then read and re-run the rows whose verdict changed.
- With k repeated runs, pass@k (at least one succeeded) and pass^k (all succeeded) answer different questions. With made-up numbers and independent runs, 75% per run gives about 98% pass@3 and about 42% pass^3. The dataset score is the share of cases that pass under the chosen rule. Report the one that matches how users meet the feature, and set its bar anew rather than copying a single-run bar.
- Analogy: a parameterised JUnit suite with a load-test-style threshold. It breaks down because an eval is a statistical sample, and because its scorer can itself be wrong.
