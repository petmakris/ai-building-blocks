# Testing notes from the first workflow

## Key points

- A workflow is your own code calling the model in an order you wrote (Anthropic: 'orchestrated through predefined code paths'). An agent is a while loop: send the system prompt, the whole conversation and the tool list, run whatever tools the reply asks for, and stop only when a reply has no tool call. A tool call is a structured field in the provider's reply (Gemini functionCall, Anthropic tool_use), not text you parse. Every call id must get exactly one result.
- The model is stateless, so every step resends the whole transcript and later steps cost more than earlier ones (Anthropic: agents use about 4x the tokens of chat, multi-agent about 15x). A slow, paid, non-deterministic component now decides control flow at run time.
- The five workflow patterns are chaining, routing, parallelization (sectioning or voting), orchestrator-workers (one plan up front, then your code runs the list) and evaluator-optimizer (draft, grade, revise up to N rounds). Each is a few lines of plain code, and your code owns the exit.
- Every loop needs a step cap the loop actually reads and that carries across a pause, a per-call timeout, a running token total turned into money with input and output priced separately, a deadline for longer runs, and a test with a fake model that always returns a tool call. Billpod: 6 steps, a 60 s stream timeout, 2048 output tokens per reply.
- Tool calls are proposals from an untrusted source, because of prompt injection. Allow-list them and check them against stored data (schema, the record exists in this household, the version the model read still matches). Have a person confirm changes to existing data, one card at a time. A decline or a 'not run' goes back to the model as a result.
- A pause or a long run needs saved state. Billpod seals the paused turn, including the step count and usage, into a signed 10-minute single-use blob; a server row works too. Durable execution (Temporal activities) records each model and tool call. After a crash it re-runs the deterministic loop code with the saved results, so it neither pays twice nor repeats side effects. This is the outbox mindset applied to every step.
- Use an agent only when the steps cannot be written down in advance. A decision that must be reliable belongs in a fixed code step outside the loop.
- Analogy: a workflow is a saga orchestrator or batch job, and an agent is a command-queue consumer whose producer is the model. The analogy breaks in three places: after a crash an agent's next command cannot be worked out again from code, every command must be checked against an allow-list and the stored data and confirmed, and each one costs money.
