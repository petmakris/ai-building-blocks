# Testing notes from the first workflow

## Key points

- The section is in sources/sections-tested/10-guardrails.html with id 'guardrails'. It has about 3,900 words including code and a table, and its tags are balanced. Round 3 is backed up at scratchpad/10-guardrails.r3.bak.html and round 2 at scratchpad/10-guardrails.r2.bak.html.
- A model obeys instructions written anywhere in the text it reads. Indirect injection plants them in a document, an email or a tool result. Direct injection is the user typing them, and it matters when the system prompt holds secrets.
- Injection cannot be escaped like SQL. A PreparedStatement keeps the query and its values in separate channels, but a model gets one token stream. Delimiters, an 'ignore instructions' line (keep it, it costs nothing) and classifiers only lower the odds. Willison: 95% is a failing grade, because attackers retry until one variant works. The response schema fixes only the answer's shape, never its values.
- A tool is a function you declare to the model. One reply can ask for several calls, and your code decides whether each one runs. A call that does not run gets an error result. The model keeps no memory, so every request resends the conversation and the results. A turn is all the model calls up to the final answer. All defences are backend code at three points: which tools are declared, what happens when a call comes back, and what the UI shows.
- Lethal trifecta: data theft needs private data, untrusted content and a way out, all together. The way out is the leg you can usually remove in code. A URL fetch and rendered Markdown images or links count as ways out. Plain text does not leak by itself but can still mislead. Unwanted writes are a separate harm, and a person approving the write defends against it.
- Billpod: the 46-name allow-list leaves out capture_invoice (it fetches any fileUrl) and get_file_url, and calling them gets UNKNOWN_TOOL. Span has no URL field. Add-only writes run at once, a bill the assistant adds gets Undo, and Billpod moves no money, so an injected IBAN still meets the person at their bank. Changing or removing a record needs a card that shows the stored old value and the new value from the call. The call is sealed in a ticket: AES-256-GCM, bound to the user and the household, holding a SHA-256 hash of the conversation, valid 10 minutes, single use. The browser holds the conversation and sends it back on Approve; the server compares the hash, so an edited history is refused, and then runs the sealed call. Reads and adds earlier in the same reply have already run, and writes after it get 'Not run'. A pending-calls table is the simpler Java equivalent. householdId comes from the session ctx, never from model arguments. QR-decoded values beat AI readings, and AI readings land in drafts a person checks.
- Input checks (length limits, classifiers, removing personal data, also run on tool results) and output checks (schema, value rules, escaping, never executing; a failed field is dropped and left empty in the draft) stop cheap attacks. They prove a value is well formed, never that it is true. Injection tests assert on outcomes, never on the model's words. The smallest version needs no classifier.
- Personal data in a prompt leaves your boundary for the provider (the company hosting the model API). Send only the fields the task needs, mask the rest (Presidio), check how long the provider keeps prompts and where it processes them, and treat prompt logs as personal-data stores. The section uses the OWASP LLM Top 10 2025 as a 10-row checklist and defines embedding and training in place. The Java analogy (validation, WAF, output encoding, DLP) breaks because a model has no fixed parser rules.
