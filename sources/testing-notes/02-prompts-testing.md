# Testing notes from the first workflow

## Key points

- A prompt is the text sent to the model on every call. The service keeps no memory, so a chat call sends the system prompt (the rules for the whole conversation), the earlier messages and the new message each time. The system prompt is a template with {{variables}} that code fills on each request, and the rendered string is what the model reads. The template, the code that computes the variables, and the rendered prompt can each cause a behaviour change.
- A change to the rendered prompt is a behaviour change that no compiler sees. Example: LOM-86 changed only the code that computes {{registerRule}}. One new sentence for role-play shifted the tutor's formal or informal address at every level, including a case nobody had reported. It was checked by a unit test and a golden diff, and reply quality was never measured. A misspelled placeholder reaches the model as literal {{name}} text, and the admin save path rejects it with a validation error. Because the model samples each next word, outputs vary between calls and cannot be asserted on like return values.
- The smallest version keeps the template in git as one constant and changes a version id on every change to the rendered text. The id is either bumped by hand or tied to a hash of the golden file by a test, so changes to variable code count too, as far as the golden cases cover each variable branch. Every result stores that version and the model id in separate fields (Tunatutor's writer_prompt_version and writer_model columns), or the log line carries them when the output is not stored. Rollback is revert and redeploy. A test rejects unknown placeholders.
- Golden tests pin the exact rendered prompt byte for byte, for fixed inputs chosen to cover every variable branch. Each intended change re-renders the golden file and records why. They pin the code copy only, so they do not catch a stale database copy. Evals are a fixed set of inputs whose replies are scored by a rule, a person or a grading model. Example: count the replies in role-play scenes that use vous. Evals judge reply quality and give a score to compare between versions, with the blocking drop decided before the run.
- A database-stored prompt lets experts edit without a deployment, with an archive and rollback (activatePromptTemplateVersion), but it creates two copies. In July 2026 (#33) a stale seed row shadowed the code constant, and production lacked rules 14 and 15. The fix deleted the seed duplicate and made the code constant the default. At every startup it overwrites a differing row only when the archive table shows no admin edit, so an admin edit wins. The reverse cost is that an admin-edited row never gets later code improvements until someone resets it from the admin screen. Drift tests fail if the seed inserts the row again or if the template holds an unknown placeholder. On this path a result is stamped with a hash of the text actually used.
- A mature prompt service (Langfuse) adds numbered versions and a production label that is moved to roll back. A short client-side cache means a label move reaches servers within about a minute. Each model call is logged with its prompt version, and a version is promoted only after an eval run passes.
- Analogy: a Spring MessageSource message plus a feature flag that selects the live variant. It breaks in three ways: the model decides what the text means, the same version can give different outputs, and a new model can change what an unchanged prompt does.
