# Testing notes from the first workflow

## Key points

- The model keeps nothing between calls: anything it 'remembers' is text the backend puts into the current request. TunaTutor rebuilds and resends the whole message list on every turn; provider-side conversation storage still resends the text, so cost, window and erasure duties remain.
- Short-term memory is the conversation transcript, keyed by conversation ID and trimmed by a sliding window (a fixed count, or a token budget) or by a summary from an extra model call. Spring AI's MessageWindowChatMemory, plugged in as an advisor, keeps 20 messages by default, saves the model's answer exactly as returned, and a call without a conversation ID throws.
- Long-term memory is facts about a user, keyed by user ID, and runs in five steps. (1) The model proposes set/delete facts in a JSON side field that cannot be fully trusted: with no JSON mode it drifts into prose, and on bad JSON you show the text and store nothing. (2) Code gates on state it controls (memory off, role-play chosen at session start). (3) A job row is queued in the same transaction as the messages. (4) A worker upserts rows keyed (userId, key) with cleaned values. (5) The newest 50 facts are loaded once into the next conversation's system prompt as plain text; reload per call to use a fact in the same chat.
- The model invents keys and only sees the facts that were injected, so it cannot update facts beyond the cap and may create duplicates. A code-side allowed-key list, also listed in the system prompt, fixes both problems.
- Every stored fact needs a scope (user, plus tenant), an expiry rule (an expiresAt, or a load cap that leaves older rows in the table) and a source tag. Users need a way to see and delete their facts, and erasure must reach summaries (delete or regenerate them), caches and logs.
- Memory poisoning: a planted fact is injected into every future prompt as a trusted instruction and can drive tool calls. The defences: extract only from the typed chat message, allow only listed keys, tag sources, show users their facts, and have tools check permissions in authorization code, never in memory.
- The backend analogy is HTTP session state (short-term) and a user profile or CRM record updated by an outbox-fed job (long-term). It breaks in three places: a model guessing from free text writes the record, a model reads it back as instructions, and derived text such as summaries holds copies of the facts.
