# Testing notes from the first workflow

## Key points

- When an LLM call goes wrong it still returns HTTP 200 with no exception. The only evidence is the exact prompt that went in and the reply that came out. Each call therefore needs one record: template name and version, requested and responding model, input, cached and output tokens, finish reason, latency, cost, the parsed result, the feature and user it is billed to, and the trace ID. The prompt and reply text are stored separately, keyed by trace ID.
- LLM calls bring five problems a REST call does not: the bug is in the text, each call has a variable price in tokens, prompts change outside code deploys, quality can drift with no deploy of yours, and traces hold users' personal data.
- Drift happens with no deploy of yours: the provider updates the model behind the same name, a provider bug hits, or the inputs change. Latency and error alerts never fire on it. You detect it with online evals: sample live calls at random (for example by a trace-ID hash, sized to about 200 scored calls a day per feature), score them off the request path (a deterministic check, a pinned checker model with a rubric, or a person), store the score keyed by trace ID, chart it per day, per prompt version and per model, and alert when it falls below its usual band.
- The smallest useful version is one structured log line per call, written from a single wrapper (failed calls included), plus a short-retention, restricted table of redacted prompt and reply text for every call. Spring AI already emits a gen_ai.client.operation observation, with prompt and completion logging off by default. A mature setup adds nested spans per step, dashboards, user feedback on traces, alerts on score and spend, and replay of stored prompts against a new model.
- The OpenTelemetry GenAI conventions name the span attributes (gen_ai.provider.name, gen_ai.request.model, gen_ai.response.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens, gen_ai.response.finish_reasons). Prompt and reply content (gen_ai.input.messages, gen_ai.output.messages) is opt-in because it is sensitive. The status is still Development, and there is no standard attribute for prompt version, so you add your own.
- Redacting by key name does not work for prompts, because personal data sits inside the prose under no sensitive key. Scrub the text itself, keep prompt text in a separate store with short retention and restricted access, and keep the metadata (tokens, cost, versions, scores) longer.
- The analogy is distributed tracing plus APM plus a billing meter. It breaks in three places: success is a judgement about the text, a model under the same name can change behaviour, and the payload is usually personal data.

The sentence now says that.
- fixed: Cached tokens: the text said cached tokens are always a subset of input tokens. That holds for Gemini (promptTokenCount includes cachedContentTokenCount), for OpenAI and for the OTel convention, but Anthropic reports cached tokens in a separate field. Added that qualifier.

The current client-inference.md defines gen_ai.prompt.name and gen_ai.prompt.version, both Conditionally Required, plus gen_ai.usage.cache_read.input_tokens. The sentence now names them.
