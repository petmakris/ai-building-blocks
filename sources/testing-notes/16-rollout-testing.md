# Testing notes from the first workflow

## Key points

- An LLM feature can fail in ways no test caught, and a wrong answer comes back as an ordinary HTTP 200 with valid JSON, so AI behaviour has to be measured on real traffic before anyone relies on it.
- Shadow mode calls the new behaviour on real requests and stores both its answer and the comparison with the current result, while the user still sees the old result. The shadow call runs in the background, its errors never reach the user and it has no side effects, so it can even be removed without any user noticing.
- Because two model answers can both be right, a shadow mismatch needs a comparison rule (such as acceptJudge: one level apart counts only when the cited turns back it) and a person reading the disagreements against a bar written in advance.
- A check can run in log mode first: it records the refusal it would have made and lets the item through. It is switched to enforce only when its measured refusal rate is under a bar written down in advance. A higher rate sends a person to read what it refused, to tell a too-strict guard from bad generated items.
- A flag that changes AI behaviour may be flipped only when an eval clears numeric bars fixed before the run, and the old behaviour stays available so the flag can be turned off again. A canary then shows the behaviour to a small share of users and compares them on quality signals (discarded, edited, thumbs-down) against a difference threshold and sample size set in advance, because error rates and latency do not show wrong answers.
- User feedback is useful only if it is stored with the exact turn, input and output it refers to (a trace ID, or session plus turn). Explicit feedback (thumbs, flags) is rare, and implicit signals (accepted, edited, retried) give more volume.
- In the data flywheel, a confirmed production failure is triaged and written down as a new eval case, so the next prompt or model change is tested against it. Because the provider can change the model without notice, the eval is rerun on a schedule, and the flag is turned off again if a bar is missed.
- The Java analogy is dark launch or Scientist, report-only validation, feature toggles and canaries, and a dead-letter queue that becomes test fixtures. It breaks in two places: two different model answers can both be right, so mismatches need a comparison rule, and quality can drift without any deploy.
