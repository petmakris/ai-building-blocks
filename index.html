For engineers putting AI into real software

One model call is easy. Depending on it is engineering.

Seventeen building blocks turn an unreliable, paid, non-deterministic model call into software you can run. Each one starts from a real failure, shows the mechanism step by step, and ends with the smallest version you can build today.

Seventeen building blocks of a modern AI application

Pick the one you need

01 · The tool layer: every action is an MCP tool

Modern apps have MCP actions built in. Your screens, your own AI and outside AIs all run the same actions.

Three kinds of caller now use your app: its screens, its own assistant and other people's assistants. How do you build each action once so all three get the same rules?

Read →02 · The model gateway

Send every model call through one gateway. It holds the keys, the fallbacks and the bill.

Every model call costs money, fails in its own ways and needs a secret key. Where does all that live?

Read →03 · Prompts as versioned configuration

Treat prompts as versioned configuration. Keep each one in one place, with a version.

Calling a model is the easy part. Keeping the words you send in one place, with a version on them, is where this app went wrong.

Read →04 · Context engineering

Choose what the model sees on every call. More text gives worse answers.

If more text makes answers worse, some code must pick, on every call, what the model sees.

Read →05 · Structured output

Make the model return typed data. Then validate it like any outside input.

Your code needs a typed record it can trust, and the model only writes text.

Read →06 · Tool calling and MCP

Let the model call your functions. Your code decides which calls run.

The model can only reply with text, and a request to run a function is structured text too. What decides whether that line pays your bills?

Read →07 · Retrieval (RAG)

Retrieval puts your own documents into the prompt. Without it, the model knows nothing about your data.

The model sees your data only through the one request you send, so how do the right passages of your wiki get into it?

Read →08 · Memory

The model forgets everything between calls. Your code keeps the memory and decides what goes in.

The model forgets every user after every call, so your code has to keep the record and decide what goes into it.

Read →09 · Workflows and agent loops

An agent is a loop of model calls. Your code sets its limits and decides when it stops.

In one call, the model can ask your code to run one of your functions, called a tool. Who makes the second call, the third, and decides it is done?

Read →10 · Human in the loop

Make risky actions wait for a person. The model proposes, a person approves.

Your agent can now change data by itself, so which of its changes should wait for a person's click?

Read →11 · Guardrails and prompt injection

Treat every document the model reads as untrusted. Guardrails stop hidden instructions from using your tools.

Your model now has tools that change records. What stops a hidden line in a document from using them?

Read →12 · Evals

Test AI features with evals. Scored runs over fixed cases show if a change helped or hurt.

After a prompt change every existing test stays green, and none of them says whether grading got better or worse.

Read →13 · Observability for LLM calls

Log every model call with its input and output. A 200 status says nothing about whether the answer was right.

A log can show what every model call cost. Nothing in it says whether the answer was right.

Read →14 · Caching

Cache the fixed start of your prompt. Put changing values last, or nothing is reused.

Your prompt is long and well built. Why pay for the same 6,000 tokens on every call?

Read →15 · Sandboxes for agents that run code

Run model-written code in a sandbox. It must never run with your service's keys.

Nobody can review code that a model writes in the middle of a request, so it needs a place where it cannot do damage.

Read →16 · Governance and model risk

Keep a record of every AI output that matters. A year later, audit will ask which model wrote it.

You can contain what the model does, but can you prove a year later what it did and who signed it off?

Read →17 · Shadow mode, flags and the feedback loop

Release AI changes in shadow mode, behind a flag. Real users find the failures your tests missed.

Your eval, a scripted run over fixed cases with the real model, passed. How does the new behaviour meet real users without betting them on it?

One request passes through the blocks in this order

Steps R0 to R13 run on every request. The rest run across requests or between releases.

Every step, with the blocks it belongs to
  1. R0

    Front door

    the request arrives through one of the front doors (the app's screens over REST, the in-app assistant, or an outside assistant over MCP); each door authenticates and builds its own context, and all of them reach the same tool layer and services

    The tool layer: every action is an MCP tool Tool calling and MCP

  2. R1

    Edge and controller

    authenticate; resolve tenant and entitlements and carry them downstream; the request carries the client-held history

    Guardrails and prompt injection Tool calling and MCP Context engineering Workflows and agent loops

  3. R2

    Admission and input guardrails

    spend cap at the activity door; PII redaction, injection or moderation classifier, topical scope; may short-circuit to a canned reply

    The model gateway Guardrails and prompt injection

  4. R3

    Cache check

    exact or semantic response cache, scoped per tenant; a hit returns at once

    Caching

  5. R4

    Router

    a cheap classifier picks the workflow and the model tier

    The model gateway Workflows and agent loops

  6. R5

    Context assembly

    system prompt from the registry with its version; trimmed history; memory facts; retrieved passages; tool definitions; stable layers first for the prompt cache; inside the token budget

    Prompts as versioned configuration Context engineering Memory Retrieval (RAG) Tool calling and MCP Caching

  7. R6

    Gateway call

    usage context check, candidate list, provider attempt with retries inside the time budget, fallback; structured output or strict tool schemas

    The model gateway Structured output Context engineering

  8. R7

    Settle and meter every attempt

    ledger rows priced at write time, allowance debit, cached-input row

    The model gateway Observability for LLM calls Caching

  9. R8

    Classify the reply

    finish reason to stop reason; text, tool calls, refused or malformed

    The model gateway Structured output Tool calling and MCP

  10. R9

    Agent or workflow loop

    run the tool calls, feed results back, call the model again; stop at a step, cost or time budget

    Workflows and agent loops Tool calling and MCP Context engineering

  11. R10

    Per-call policy before a tool runs

    validate arguments, scope to the caller's tenant, refuse unknown tools; model-written code goes to the sandbox

    Guardrails and prompt injection Tool calling and MCP Sandboxes for agents that run code

  12. R11

    Human in the loop

    a risky write becomes a sealed card, the turn pauses, the person approves, rejects or changes, the turn resumes

    Human in the loop Workflows and agent loops Context engineering Tool calling and MCP Guardrails and prompt injection

  13. R12

    Output handling

    schema and business validation, output guardrails, escape before rendering, never auto-load URLs

    Structured output Guardrails and prompt injection

  14. R13

    Response and memory write-back

    Memory

  15. R14

    Tracing and the call record (cross-cutting)

    one record per model call with text, model and prompt version, tokens, cost, latency; the trace is also the audit log
