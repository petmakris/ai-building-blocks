Block 17 · Shadow mode, flags and the feedback loop

Release AI changes in shadow mode, behind a flag. Real users find the failures your tests missed.

A prompt is the instruction text the app sends to the model. A model that gives a wrong answer still returns HTTP 200 with well-formed JSON, in normal time. Error rates, exceptions and latency stay flat. The feature passed every test before release. Real users send inputs no test set covered, so the first one to see the failure is a user.

The whole picture

The idea

New AI behaviour earns its way to users in stages: it first runs unseen on real traffic (shadow mode), a flag turns it on only when measured numbers clear a bar written down beforehand, and every confirmed failure becomes a new test case.

In a classic backend, shadow mode is a dark launch, or GitHub's Scientist library. Scientist runs new code next to the current code, returns the current result and logs mismatches. The analogy breaks on mismatches: two different model answers can both be right. So a mismatch needs a rule in code and a person to judge it.

Watch it happen

In Lomem's language app, a tutor chats with a learner. Rules in code place the learner at a level from A1 (beginner) to B2, and the learner sees that level. The judge grades the same chat in shadow mode, so the learner still sees the rules' level. The chat below is real test data from the code. The readout numbers in step 6 are made up.

Each step in full, with its sources
Step 1

Start the judge once, then answer without waiting

When the chat reaches its wind-down, or is force-closed, the server claims the judge: it writes a start time in the database. The claim succeeds only once, so the judge runs at most once per chat. The server starts the judge in the background. It returns the tutor's reply without waiting.

F1.4 · F1.5 · F1.6 · F1.8 · C10 · C12

Step 2

The judge reads the answers, never the rules' level

A turn is one tutor question plus the learner's answer. Each answer already carries facts: fields such as its text type and whether its meaning was clear. The judge gets the answered turns and their facts. It never gets the rules' level, so it cannot copy it. It replies in JSON with a level and its cited turns, the turns it relied on.

F2.1 · F2.2 · F2.3 · C10 · C41 · X5 · M18 · E1

Step 3

Check in code whether the judge's level is backed by evidence

A judge two or more levels away from the rules is rejected. A judge one level up needs two things. First, at least two cited turns whose facts pass the code's check for that level. Second, no question at that level that the learner failed.

Real test case. Had the judge cited only turn 5, the verdict would be rejected.

F3.1 · F3.4 · F3.5 · F3.6 · F3.7 · E1 · C11 · C40

Step 4

Store the comparison next to the answer

The server stores the judge's level and whether it would change the rules' level. It writes only the judge's own columns. Later, someone can count disagreements without re-running anything.

F2.7b · C13 · M3 · K6

Step 5

The learner still sees the rules' level

Nothing the judge says reaches the learner yet. If the judge fails, the server logs it, stores nothing and keeps the rules' level.

F2.8 · F2.9 · F2.10 · F4.5 · C9 · C14 · Q1

Step 6

A person reads the disagreements against a bar written first

Once enough chats have run, the team counts the stored disagreements. A person reads each one and notes whether the judge or the rules placed the learner right. If the judge clears the bar, a flag shows learners the judge's accepted level. If not, the judge is dropped.

Take away

4 things to remember

1

Wrong answers look like right ones

A wrong answer is a fast HTTP 200 with valid JSON, so error rates and latency miss it. Measure what users do with the answer instead: edit it, discard it, retry it.

P1 · C25 · M6
2

Shadow first, off the request path

Run the new behaviour in the background, with no side effects. Store the comparison while users see the old result.

C9 · C12 · C13 · M3
3

Write the bar before the numbers

A flag flips only when an eval clears bars fixed in advance.

4

Failures become eval cases

A confirmed failure, stored with the turn it is about, becomes a new eval case.

The trap

Counting every mismatch as an improvement

What people assume

"The new model answered differently, so it caught what the old behaviour missed."

So the team counts mismatches, as GitHub Scientist does for code, and ships when the count looks high.

What actually happens

Two model answers can both be right, so a mismatch is not a bug in the old answer.

Count a difference only when a rule in code finds evidence for it. Have a person read the disagreements against a bar written before reading.

M5 · M7 · C11 · C39 · P4

Build it

The smallest shadow mode is one async method and one flag

Compute the current result, grade it again in the background, compare in code, store the new result and the comparison, and flip a flag only after the readout. This Java sketch is for teaching. Lomem's real code is TypeScript.

public Level placement(Chat chat) {
  Level current = rules.level(chat);                         // the rules' level, which the user sees
  if (NEW_GRADER_ON) return candidateOrCurrent(chat, current); // 6 flipped only after the readout
  shadow.shadowGrade(chat, current);                         // 1 start, don't wait
  return current;                                            // 5 the user still sees the rules' level
}

@Async   // a separate thread pool, never the request thread
public void shadowGrade(Chat chat, Level current) {
  try {
    Level candidate = grader.grade(chat);                    // 2 gets the chat, never `current`
    boolean candidateWins = comparisonRule.candidateWins(current, candidate); // 3 evidence check in code
    chatRepository.saveShadow(chat.id(), candidate, candidateWins);           // 4 level and comparison
  } catch (Exception e) {
    log.warn("shadow grader failed, current level stands", e); // 5 failure keeps the rules' level
  }
}

Each [n] marks the code for walkthrough step n. The sketch skips step 1's claim, so the same chat can be graded twice. Lomem claims the chat first: it sets judge_started_at only where it is still empty.
