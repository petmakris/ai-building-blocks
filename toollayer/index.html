Block 01 · The tool layer: every action is an MCP tool

Modern apps have MCP actions built in. Your screens, your own AI and outside AIs all run the same actions.

People no longer use an app only through its screens. They also ask an AI assistant inside the app to do things, and outside assistants such as Claude or ChatGPT reach the app over MCP (Model Context Protocol, a standard way for an AI to call another app's functions). So build each action once, as a tool: a named function with typed inputs, such as pay_bill(bill_id). Your own assistant and outside assistants call that tool. The tool calls the same service function that the screen's button calls, so the same rules apply to all three. Billpod, a household-bills app, is built this way.

The whole picture

The idea

Define each operation once, as a typed tool that calls the same service your screens' routes call. Send every AI call through one function, the runner. Each door then adds only its own policy: its own extra rules, such as asking the person first.

In backend terms, the tool layer is a second controller layer next to the REST controllers, over the same services. The runner is its one dispatcher for every AI caller. The difference: the caller is a model that picks the operation from a sentence.

Each step in full, with its sources
Step 1

The in-app door builds the caller's context

Ask Billpod is the assistant inside the app. Behind it, Billpod sends the person's message to a language model. Before any tool runs, it builds one context object. The context says who is asking, which household they belong to, which permissions (scopes) they hold, and which door they came through. The household is found the same way every REST request finds it.

F3.1 · F3.2 · C8 · C9

Step 2

This door's own rule: a card before any change

Billpod sends the model a list of tools, each with a name, a description and an input schema. The model replies with a request: run mark_paid with these arguments. Billpod's code decides whether and how it runs. That tool is on Ask Billpod's confirm list, so it does not run yet. The person sees a card built from the stored bill and presses Approve. The confirm list belongs to this door, not to the tool.

F3.4 · F3.5 · C16

Step 3

The approved call goes into the one runner

Every AI door hands its calls to the same function, runTool. It checks the scopes. It validates the arguments against the tool's schema. Then it runs the handler, the tool's own code. Every failure comes back as a result the model can read.

F3.6 · C7

Step 4

The handler calls the service the Pay button calls

The handler does not write to the database itself. It calls bills.pay, the same service function the app's REST route calls when someone presses Pay on the screen. The rules live there, such as the household filter and "already paid". The handler then returns the updated bill.

F3.7 · C6 · X10 · X11 · X12

Step 5

An hour later, from Claude: another door, the same tool

The person forgot the earlier payment and asks Claude to pay the same bill. Claude runs its own model and reaches Billpod over MCP (Model Context Protocol), the standard way an outside assistant calls an app's tools. It reads the bill through one of Billpod's read tools, then calls mark_paid. Billpod's MCP endpoint checks Claude's access token and builds the same kind of context as the in-app door. Only the scopes and the caller kind differ.

F4.1 · F4.2 · F4.4 · C12 · X35

Step 6

Here the confirmation is Claude's, not Billpod's

Billpod draws no card inside Claude. The mark_paid tool carries the hint destructiveHint: true. Its description says to confirm with the person first. Whether Claude asks is up to Claude, not Billpod. What still applies on this door: the token's scopes, the runner's input check and the service's own rules.

F4.3 · C17 · X35 · Q2

Step 7

Same runner, same service, same refusal

The call goes through the same runner to the same service, and the service refuses it: the bill was paid an hour ago. That rule lives in the service, so no door can skip it. The runner hands the refusal back to Claude as an error it can read. The Pay button on the screen would get the same "already paid" through its route.

Take away

5 things to remember

1

Three doors, one set of rules

The screens, the in-app assistant and outside assistants perform the same operations. The rules live in the services, and both the routes and the tools call them.

C1 · C6 · X1 · X2
2

Define each tool once

A tool is one defineTool call: its spec (name, description, input schema, scopes, hints) plus a handler that calls a service. One list feeds both AI doors, and one runner runs every AI call.

C3 · C4 · C5 · C7 · X7
3

Policy belongs to the door

A card in Billpod's chat, a hint to Claude. Whatever must hold on every door goes in the service.

C16 · C17 · Q2
4

A test keeps the doors level

Billpod's parity test reads every route under /api/billpod from the web framework. It fails on a route that is neither mapped to a tool nor excluded with a reason. Routes outside that path, such as sign-in and /mcp, are not checked.

C14 · C15 · X3 · X3b · X23 · X24
5

Rules kept in a door do not reach the other doors

A rate limit on a route does not guard a tool. Move the rule into the service, or copy it into the tool on purpose, as Billpod did for invoice uploads.

C19 · M2 · X4 · X26

The trap

Same tools, so the same safety

What people assume

"The assistant and the MCP server share one tool list, so Billpod's confirmation card protects both."

The team relies on the card and lets MCP serve every write tool.

What actually happens

The card belongs to the in-app door only.

Over MCP, Billpod can only send a destructiveHint and an instruction. The MCP specification tells clients to treat such hints as untrusted unless the server is trusted, so Claude may ignore them. On the MCP door the token's scopes, the runner's input check and the service's rules still bind. Only the service's rules, such as the household filter and "already paid", hold on all three doors.

C7 · C16 · C17 · E4 · M4 · Q2

Build it

The smallest tool layer is one list, one runner and thin doors

One tool defined once, the screen's route calling the same service, and two AI doors that differ only in their context and their own policy. This TypeScript sketch is shaped after Billpod's code, with made-up names such as CONFIRM and card.

const markPaid = defineTool({                                         // 1 spec + handler, defined once
  name: "mark_paid", scopes: ["billpod:write"], annotations: { destructiveHint: true },
  input: z.object({ billId: z.string(), version: z.number(), paidVia: z.string() }), // zod schema
  handler: (input, ctx) => bills.pay(ctx.householdId, input.billId, input), // 2 the service the route calls
});
const TOOLS = [markPaid /* , every other tool */];

app.post("/bills/:id/pay", (req) => bills.pay(req.householdId, req.params.id, req.body)); // 3 the screens' door

async function inApp(call: ToolCall, userId: number) {                // 4 the in-app door builds its context
  const ctx = { userId, scopes: ALL_SCOPES, caller: "assistant", householdId: await householdOf(userId) };
  if (CONFIRM.has(call.name)) return card(call);                      // 5 this door's own policy: a card first
  return runTool(findTool(TOOLS, call.name)!, call.args, ctx);        // 6 the one runner
}
async function overMcp(call: ToolCall, token: AccessToken) {          // 7 the MCP door builds its context from the token
  const ctx = { userId: token.userId, scopes: token.scopes, caller: "mcp", householdId: await householdOf(token.userId) };
  return runTool(findTool(TOOLS, call.name)!, call.args, ctx);        // 6 the same runner, no card here
}

[1] is C4. [2] is C6. [3] is C13. [4] and [7] are C9, each door building its own context. [5] is C16. [6] is C7. This sketch leaves out two things Billpod's code does. findTool can return nothing, and Billpod's MCP door answers that with a NOT_FOUND error. Billpod's MCP door checks the OAuth token and refuses a call whose token lacks the tool's scope.
