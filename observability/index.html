Block 13 · Observability for LLM calls

Log every model call with its input and output. A 200 status says nothing about whether the answer was right.

A language app asks a model (an LLM, a service that takes text and returns text) to grade a learner's Portuguese. In this made-up incident, learners type Eu sou um barista., which is correct, and the app marks it wrong. Nothing was deployed for a week, the logged call returned 200 in 1.4 seconds, and the error tracker is empty.

The whole picture

The idea

Write one record per model call with the exact text, the prompt version (which revision of your instructions to the model was sent) and the model that actually answered. Then score a sample of live calls to catch quality drops that no deploy of yours explains.

It is distributed tracing plus APM plus a billing meter. The model call is one more timed downstream call. It also carries tokens (the units of text the vendor bills by) and cost. The analogy breaks at correctness. APM counts a fast 200 as a success, but a model's reply can be fast, return 200 and still be wrong. So you keep the reply text and score it, which APM never does.

Watch it happen

A model changes behind its name. Here is how the records catch it.

Each step in full, with its sources
Step 1

A wrong grade comes back as a success

On Monday morning Google points the alias at a preview (pre-release) model. The grading feature now marks correct answers wrong. Every call is fast, returns 200 and throws nothing.

F1.6 · F1.7 · E1 · P2

Step 2

The wrapper writes one record per call

Every model call goes through one wrapper, a single function in your code. It logs the prompt version and the model the reply says answered, not only the one requested. It also stores the prompt and reply with names and emails scrubbed out. That text goes to a restricted table kept 14 days.

The response model name gemini-2.5-flash-preview-09-2025 is real.

F1.11 · F1.14 · C15 · E2 · N16

Step 3

A second model scores a 2% sample

Calls that finished normally (finish reason STOP, not failed and not cut off at the length limit or by the content filter) enter a random 2% draw. Drawn calls go on a queue, off the request path. A checker model, a second pinned model, reads the redacted text, the grader's verdict and a rubric (a written list of what counts as correct). It answers AGREE if the verdict is correct and DISAGREE if not, stored as 1 or 0.

F1.15 · F2.4 · F2.6 · C17 · C25 · N17 · M6 · M11

Step 4

The nightly job sees Monday fall below its band

The agreement rate is the share of a day's scored calls where the checker agrees with the grader's verdict. The alert line is 0.92. It sits three standard deviations (how far the rate usually moves) below the rate's 30-day mean. Monday scores 0.81, so the alert fires at 06:00 Tuesday. The first learner reports come that afternoon.

F2.7 · F2.8 · C29 · C30 · N20 · N21 · N23 · N24 · N25 · Q9

Step 5

Grouping by version shows the model moved

The prompt version is 14 on every call, so no prompt edit caused it. The response model changes on Monday. With it, the share of answers graded wrong goes from 4% to 19%. The stored text lets the owner read the five reported calls.

F3.2 · F3.4 · C15 · N26 · Q7

Step 6

Pin the model and replay ten times

The team requests a fixed version name instead of the alias. The same prompt can give a different reply each run, so the owner replays each of the five stored prompts ten times. All fifty runs pass. The barista case joins the test set.

Take away

4 things to remember

1

A wrong answer returns 200

The call is fast, throws nothing and leaves the error tracker empty. Only a quality score catches it.

P2 · P7 · Q16 · M5
2

Pin the checker and bill it

A checker on a moving alias changes along with the model it checks. Send its calls through the same wrapper under their own feature name, so its cost shows.

M11 · M12
3

Score about 200 calls a day

That keeps chance noise near 1.5 percentage points of the agreement rate. 200 is 2% of 10,000 calls a day, or 20% of 1,000. Score from a queue, never inside the request.

C31 · E4 · E10 · N18 · N19 · M6
4

Redact names inside the prompt text

A prompt is one long text field with names and emails under no sensitive key. Redact the text itself and keep it in a restricted table.

P8 · M4 · M10

The trap

Keeping the text only for the sampled calls

What people assume

"We score 2% of calls, so we only need the text of those 2%."

So the wrapper saves prompt and reply only when a call is picked for scoring.

What actually happens

With a 2% sample, a reported call is almost never in it.

Store the redacted text of every call for a short window, 14 days in the example, so the owner can read the five reported calls. Sample only the scoring.

M7 · Q1 · N16 · E1

Build it

The smallest version is one wrapper that writes a record per call

Record the call, keep the redacted text, and sample it for scoring. This Java sketch is shortened from the made-up wrapper in example E9. It is a teaching sketch, not production code.

static final String MODEL = "gemini-2.5-flash";             // 6 a fixed name, never an alias
public GradeResult grade(GradeRequest req, long userId) {
  Prompt prompt = prompts.get("translation_grade");         // name, version, text from the DB
  String text = prompt.render(req), traceId = tracer.currentSpan().context().traceId();
  long start = System.nanoTime();
  ModelReply reply = null; GradeResult result = null;
  try {
    reply = client.call(MODEL, text);                       // 1 a wrong answer is still a 200
    return result = parse(reply.text());
  } finally {
    long latencyMs = (System.nanoTime() - start) / 1_000_000;
    CallRecord rec = CallRecord.of(traceId, "translation_grading", userId,
        prompt, MODEL, reply, result, latencyMs);           // 2 response model read from reply
    callLog.write(rec.withCost(prices.cost(rec)));          // 2 one line per call, failures too
    callText.save(traceId, redactor.scrub(text),             // 2 redacted text, every call
        reply == null ? null : redactor.scrub(reply.text()));
    if (result != null && "STOP".equals(rec.finishReason())
        && Math.floorMod(traceId.hashCode(), 100) < 2) evalQueue.send(traceId); // 3 finished normally, 2% drawn
  }
}

The checker (step 3), the nightly job (step 4) and the query (step 5) run over these records, outside the wrapper. One gap to fix before production: if the code in finally throws, its exception replaces the call's return value or the call's own exception. It needs its own try and a logged warning.
